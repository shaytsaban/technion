מה האפליקציה שאנחנו בונים?

לפני הכל — בואו נבין את המוצר. MatchMe היא אפליקציית דייטים.

💘 מה המשתמש עושה?

  1. נרשם — מזין אימייל וסיסמה
  2. יוצר פרופיל — שם, גיל, עיר, תמונה, ביו
  3. מדפדף — רואה פרופילים של אנשים אחרים
  4. עושה Like — לוחץ ❤️ על פרופיל שאהב
  5. מקבל Match — אם שני הצדדים עשו Like, נפתח צ'אט

🎯 למה צריך בסיס נתונים?

כל פעולה ברשימה למעלה — היא בעצם שינוי בנתונים.

כשמשתמש נרשם → צריך לשמור את האימייל והסיסמה שלו.

כשעושה Like → צריך לזכור מי אהב את מי.

כשיש Match → צריך לדעת ששני ה-Likes קרו.

בסיס הנתונים הוא ה"זיכרון" של המערכת. בלעדיו — כל רענון דף מוחק הכל.

📋 אפיון עסקי = מסמך שמתאר מה המערכת צריכה לעשות

זה לא קוד. זה לא טבלאות. זה טקסט בעברית שמתאר: מי המשתמשים, מה הם יכולים לעשות, ואילו חוקים יש במערכת.

🤔 למה מתחילים מזה?

כי אי אפשר לבנות טבלאות אם לא יודעים מה המערכת עושה. זה כמו לבנות ארון בלי לדעת מה צריך להיכנס לתוכו — בגדים? ספרים? כלים?

📝 דוגמה לקטע אפיון

"המשתמש נכנס למסך דפדוף. המערכת מציגה לו פרופילים של משתמשים אחרים באותה עיר, בטווח גילאים שהוא הגדיר. המשתמש יכול לעשות Like או לדלג. אם שני משתמשים עשו Like אחד לשני — נוצר Match והם יכולים לשלוח הודעות."

💡 שימו לב: האפיון כתוב בשפה רגילה. אין בו מילים טכניות כמו "טבלה" או "SQL". הוא מתאר מה קורה, לא איך.

שלב 1: מהאפיון — מזהים "ישויות"

🔍 מה זו "ישות" (Entity)?

ישות = דבר שצריך לשמור עליו מידע. בדרך כלל שם עצם שחוזר באפיון. אם אפשר לשאול עליו "כמה יש?" או "מה הפרטים של...?" — זו כנראה ישות.

נסו את זה: קראו את האפיון וסמנו שמות עצם

המשתמש בוחר להיכנס למסך דפדוף בפרופילים. המערכת מאתרת פרופילים מתאימים לפי העדפות המשתמש. המשתמש מבצע Like או דילוג, ואם יש Like הדדי נוצרת התאמה (Match).

שלב 2: למה צריך להגדיר קשרים בין ישויות?

🤝 מה זה "קשר" (Relationship)?

קשר מתאר איך שתי ישויות מתקשרות. למשל: "משתמש יוצר פרופיל" או "משתמש שולח Like". הקשר אומר לנו: כמה מהצד הזה מתקשרים לכמה מהצד השני.

❓ למה זה חשוב?

כי הקשר קובע איך הטבלאות ייבנו. אם משתמש אחד יכול לשלוח 100 Likes — צריך לתכנן את טבלת ה-Likes בהתאם. אם כל משתמש יש לו פרופיל אחד בדיוק — זה עיצוב אחר.

🔑 שני מושגים שצריך להכיר

מפתח ראשי (Primary Key) — מספר ייחודי שמזהה כל שורה בטבלה. כמו תעודת זהות. בלעדיו אי אפשר לדעת איזו שורה היא איזו.

מפתח זר (Foreign Key) — שדה שמצביע על מפתח ראשי בטבלה אחרת. אומר: "השורה הזו שייכת לשורה ההיא". למשל: פרופיל עם user_id = 5 שייך למשתמש מספר 5.

שלושה סוגי קשרים — עם דוגמאות מהחיים

1:1 — אחד לאחד

כל משתמש יש לו פרופיל אחד. כל פרופיל שייך למשתמש אחד.

בטבלאות: טבלת profiles תכיל שדה user_id שמצביע על users.

users.id ───── profiles.user_id

1:N — אחד לרבים

משתמש אחד שולח הרבה Likes. אבל כל Like נשלח ע"י משתמש אחד.

בטבלאות: טבלת likes תכיל from_user_id שמצביע על users.

users.id ─ - - - likes.from_user_id (הרבה)

N:M — רבים לרבים

משתמש עושה Like להרבה אחרים, וכל אחד מקבל Like מהרבה.

בטבלאות: טבלת likes עצמה היא טבלת קישור! היא מחברת שני users.

users ← likes(from,to) → users
💡 הסוד של N:M: תמיד פותרים אותו עם טבלת קישור. טבלת likes היא בדיוק זה — טבלה שמחברת שני משתמשים.

הקשרים ב-ERD — מה כל קו אומר

הקווים ב-ERD הם לא קישוט. כל קו אומר: "הטבלה הזו מכילה מפתח זר שמצביע על הטבלה ההיא".

👤 USER 1:1 📇 PROFILE

profiles.user_id → users.id  |  פרופיל אחד לכל משתמש  |  קו רציף = קשר ישיר אחד-לאחד

👤 USER 1:N ❤️ LIKE (from)

likes.from_user_id → users.id  |  משתמש אחד שולח הרבה likes  |  קו מקווקו = "הרבה"

👤 USER 1:N ❤️ LIKE (to)

likes.to_user_id → users.id  |  משתמש אחד מקבל הרבה likes

👤 USER N:M 👤 USER (דרך likes)

users ← likes → users  |  טבלת likes היא טבלת קישור — מחברת שני משתמשים

מה זו "טבלה" בבסיס נתונים?

📊 טבלה = גיליון מסודר עם חוקים

דמיינו גיליון אקסל, אבל עם חוקים נוקשים: כל עמודה חייבת להיות מסוג מסוים (מספר, טקסט, תאריך), ואי אפשר להכניס סתם מה שבא לכם.

🔍 שימו לב

כל שורה = משתמש אחד. כל עמודה = סוג מידע אחר. ה-id הוא מספר ייחודי — אף שני משתמשים לא יקבלו אותו id. זה מה שנקרא מפתח ראשי.

מה זו טבלה14
15 B · טבלאות

איך יוצרים טבלה — CREATE TABLE שורה אחר שורה

הפקודה CREATE TABLE אומרת לבסיס הנתונים: "תכין לי מבנה חדש לאחסון נתונים".

CREATE TABLE users (
"תכין לי טבלה חדשה בשם users"
id SERIAL PRIMARY KEY,
עמודה בשם id. SERIAL = מספר שעולה אוטומטית (1,2,3...). PRIMARY KEY = זה המזהה הייחודי של כל שורה — אסור שיהיו שתי שורות עם אותו id.
email VARCHAR(255) UNIQUE NOT NULL,
עמודה בשם email. VARCHAR(255) = טקסט באורך מקסימלי 255 תווים. UNIQUE = אף שני משתמשים לא יכולים להיות עם אותו אימייל. NOT NULL = חובה — אי אפשר להירשם בלי אימייל.
password VARCHAR(255) NOT NULL,
עמודה בשם password. טקסט עד 255 תווים (הסיסמה המוצפנת). NOT NULL = חובה.
created_at TIMESTAMP DEFAULT NOW(),
עמודה בשם created_at. TIMESTAMP = תאריך ושעה. DEFAULT NOW() = אם לא ציינת מתי — תשים את הרגע הנוכחי אוטומטית.
is_active BOOLEAN DEFAULT TRUE
עמודה בשם is_active. BOOLEAN = אמת או שקר (true/false). DEFAULT TRUE = ברירת מחדל: המשתמש פעיל.
);
סוגרים את הגדרת הטבלה.

16 B · טבלאות

טבלת likes — טבלת קישור בין משתמשים

זו טבלה מיוחדת: היא לא שומרת מידע על "דבר" — אלא על קשר בין שני משתמשים.

CREATE TABLE likes (
"תכין לי טבלה בשם likes"
id SERIAL PRIMARY KEY,
מזהה ייחודי לכל like. מספר אוטומטי.
from_user_id INT REFERENCES users(id),
מי שלח את ה-like. INT = מספר שלם. REFERENCES users(id) = המספר הזה חייב להיות id של משתמש שקיים בטבלת users. זה מפתח זר — הוא "מקשר" לטבלה אחרת.
to_user_id INT REFERENCES users(id),
מי קיבל את ה-like. גם זה מפתח זר ל-users. שימו לב: שני השדות מצביעים על אותה טבלה — כי like הוא בין שני משתמשים.
created_at TIMESTAMP DEFAULT NOW(),
מתי נשלח ה-like — אוטומטי.
UNIQUE(from_user_id, to_user_id)
השילוב של "מי שלח" + "למי" לא יכול לחזור. כלומר: אותו משתמש לא יכול לעשות Like פעמיים לאותו אדם.
);
סוגרים.
💡 REFERENCES זה מה שמונע באגים: אם תנסו לעשות like למשתמש שלא קיים — בסיס הנתונים יסרב. זה נקרא "שלמות referential".

שלושה מושגים שחוזרים — להבין פעם אחת

🔑

PRIMARY KEY

המזהה הייחודי של כל שורה. תמיד יש אחד בכל טבלה. בדרך כלל קוראים לו id.

למה צריך? כי בלי מזהה ייחודי — אי אפשר לדעת איזו שורה היא איזו. אם יש שתי "דנה" בנות 27 מחיפה — איך תדעו מי זו מי?

🔗

FOREIGN KEY (REFERENCES)

שדה שמצביע על מפתח ראשי בטבלה אחרת. אומר: "הערך כאן חייב להיות id קיים שם".

למה צריך? כי זה מונע נתונים "יתומים". אם מוחקים משתמש — בסיס הנתונים יודע למחוק גם את כל ה-likes שלו.

🚫

UNIQUE

אומר: "הערך (או השילוב) הזה לא יכול לחזור על עצמו".

למה צריך? כי אימייל צריך להיות ייחודי (UNIQUE על עמודה אחת), וגם Like כפול לא הגיוני (UNIQUE על שילוב של שתי עמודות).

מה זה SQL ולמה זה נראה ככה?

🗣️ SQL = שפה לשאול ולשנות נתונים

SQL (Structured Query Language) היא שפה שנראית כמו אנגלית פשוטה. היא נבנתה כדי שאנשים (לא רק מתכנתים) יוכלו לשאול בסיס נתונים שאלות.

📖 דוגמה: איך SQL נראה כמו אנגלית

בעברית: "תביא לי את השם והגיל של כל מי שגר בחיפה"

ב-SQL: SELECT name, age FROM users WHERE city = 'חיפה'

SELECT = "תביא לי"  |  FROM = "מתוך"  |  WHERE = "שבהם"

🔤 4 הפעולות הבסיסיות

SELECT — לקרוא נתונים (הכי נפוץ)

INSERT — להוסיף שורה חדשה

UPDATE — לשנות שורה קיימת

DELETE — למחוק שורה

INSERT — איך מוסיפים שורה חדשה

Use Case: משתמש חדש נרשם לאפליקציה. צריך להוסיף אותו לבסיס הנתונים.

השאילתה — עם הסבר:

INSERT INTO users
"תכניס לתוך טבלת users"
(name, age, city)
את העמודות האלה: שם, גיל, עיר (לא חייבים את כולן — id נוצר אוטומטית)
VALUES
"הערכים שאני רוצה להכניס הם:"
('רון', 26, 'חיפה');
רון, בן 26, מחיפה — הסדר חייב להתאים לסדר העמודות למעלה!

התוצאה: שורה חדשה נוספה עם id=5 (הבא בתור).

⚠️ חשוב: הסדר של הערכים ב-VALUES חייב להתאים בדיוק לסדר העמודות שציינתם. אם כתבתם (name, age, city) — אז הערכים צריכים להיות (שם, גיל, עיר) באותו סדר.

UPDATE — איך משנים שורה קיימת

Use Case: משתמש רוצה לעדכן את הביו שלו.

השאילתה — עם הסבר:

UPDATE profiles
"תעדכן בטבלת profiles"
SET bio = 'אוהבת לטייל'
"תשנה את עמודת bio לטקסט 'אוהבת לטייל'"
WHERE user_id = 42;
"אבל רק בשורה שבה user_id שווה 42" — בלי זה, הייתם משנים את הביו של כולם!
⚠️ חשוב מאוד: כל UPDATE בלי WHERE — משנה את כל השורות בטבלה. אם תכתבו UPDATE profiles SET bio = 'hello' בלי WHERE — כל המשתמשים יקבלו את אותו ביו. תמיד תבדקו פעמיים שיש WHERE.

JOIN — איך מחברים שתי טבלאות

🤝 מה זה JOIN ולמה צריך אותו?

עד עכשיו שאלנו שאלות על טבלה אחת. אבל מה אם אנחנו רוצים מידע משתי טבלאות ביחד? למשל: "תראה לי את השם של כל מי שעשה לי Like" — השם נמצא ב-users, ה-Like נמצא ב-likes. צריך לחבר.

שתי טבלאות:

users
idname
1דנה
2יואב
3מאיה
likes
from_user_idto_user_id
12
21
13
SELECT u.name, l.to_user_id
תחזיר את השם (מ-users) ואת מי קיבל את ה-like (מ-likes)
FROM users u
תתחיל מטבלת users, ותקרא לה בקיצור "u"
JOIN likes l
תחבר אליה את טבלת likes, תקרא לה בקיצור "l"
ON l.from_user_id = u.id;
החיבור: קח שורות שבהן ה-from_user_id ב-likes שווה ל-id ב-users. כלומר: התאם כל like למשתמש ששלח אותו.

פלט: דנה→2, יואב→1, דנה→3

סוגי JOIN — מה ההבדל?

INNER JOIN (סתם JOIN)

רק שורות שיש להן התאמה בשתי הטבלאות.

דוגמה: משתמש + הפרופיל שלו — רק למי שיש פרופיל.

users: [1,2,3] ← INNER → profiles: [1,3]
פלט: רק 1 ו-3 (ל-2 אין פרופיל)

LEFT JOIN

כל מה שבטבלת שמאל, גם אם אין התאמה בימין. במקום שאין התאמה — יופיע NULL (ריק).

דוגמה: כל המשתמשים, גם אלה עם 0 Likes.

users: [1,2,3] ← LEFT → profiles: [1,3]
פלט: 1, 2 (NULL), 3

SELF JOIN

טבלה מצטרפת לעצמה. נשמע מוזר? זה שימושי!

דוגמה: למצוא Match הדדי — שני Likes הפוכים בטבלת likes.

likes: 1→2 וגם 2→1 = Match!

GROUP BY — לספור, לסכם, לקבץ

📊 מתי משתמשים ב-GROUP BY?

כשהשאלה שלכם מתחילה ב"כמה", "מה הממוצע", "מה המקסימום" — אתם צריכים GROUP BY. הוא מקבץ שורות דומות ואז מסכם אותן.

טבלת likes:

idfrom_user_idto_user_id
11 (דנה)2 (יואב)
21 (דנה)3 (מאיה)
32 (יואב)1 (דנה)
43 (מאיה)1 (דנה)
51 (דנה)5 (רון)

שאילתה: כמה Likes כל משתמש נתן?

SELECT from_user_id, COUNT(*) AS total_likes
תחזיר: את מי ששלח + ספירה של כמה שורות. COUNT(*) = "תספור את כל השורות". AS total_likes = "תקרא לעמודה בשם total_likes"
FROM likes
מתוך טבלת likes
GROUP BY from_user_id
תקבץ לפי from_user_id — כלומר, תאסוף את כל השורות של אותו שולח ותספור אותן ביחד
ORDER BY total_likes DESC;
תסדר את התוצאות מהגבוה לנמוך. DESC = descending = יורד

פלט: דנה=3, יואב=1, מאיה=1

תת-שאילתות — "שאילתה בתוך שאילתה"

🔄 מה זו תת-שאילתה?

לפעמים כדי לענות על שאלה, צריך קודם תשובה לשאלה אחרת. תת-שאילתה היא שאילתה שרצה בתוך שאילתה אחרת — התוצאה שלה משמשת את החיצונית.

📝 דוגמה: "תמצא לי את כל הפרופילים שאני לא חסמתי"

כדי לענות, צריך קודם לדעת: מי חסמתי? (תת-שאילתה) ואז לסנן אותם (שאילתה חיצונית).

SELECT *
תחזיר את כל העמודות
FROM profiles
מתוך טבלת הפרופילים
WHERE user_id NOT IN (
סנן: רק פרופילים שה-ID שלהם לא נמצא ברשימה הבאה:
SELECT blocked_user_id
הרשימה: כל המשתמשים שמישהו חסם (זו התת-שאילתה!)
FROM blocks
מתוך טבלת החסימות
WHERE user_id = 42
אבל רק החסימות של משתמש 42
);
סוגרים את התת-שאילתה. בסיס הנתונים קודם מריץ את הפנימית, ואז משתמש בתוצאה לסינון.

API = תפריט מנות של תוכנה

🍽️ אנלוגיה פשוטה

כשאתם הולכים למסעדה — אתם לא נכנסים למטבח. אתם פותחים תפריט, מזמינים מנה, ומקבלים אותה. API זה אותו דבר: תפריט של בקשות שתוכנה מוכנה לקבל, ותשובות שהיא מבטיחה להחזיר.

לכל מודל AI יש API. מהקוד של MatchMe תוכלו לקרוא ל-Claude ולקבל תשובה — בלי שמישהו ייפתח דפדפן. האפליקציה שלכם מדברת עם AI ישירות, ברקע.
