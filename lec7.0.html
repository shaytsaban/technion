Section 2 · Environment Protection

The Missing Toy Bricks Trap (Dependencies)

Analogy: Blueprinting a LEGO castle vs. having the actual bag of gold bricks in your room.

In our last lecture, many students ran into instant crashes with bright red error messages. They saw names like ModuleNotFound or ImportError. Let's explain why this happens using a simple analogy:

The Toy Box Analogy:

Your application files are blueprint maps for building a toy fortress. If you don't have the physical toy blocks installed on your bedroom shelf, you can't construct it! In software development, those physical blocks are called dependencies.

In Google Antigravity, while our agent handles the heavy lifting, your local system still needs its package libraries (like the google-antigravity SDK) loaded inside a secure sandbox called a Virtual Environment (venv).

What is a Virtual Environment (venv)?

Think of a virtual environment as a Private Workspace Tent inside your computer. It prevents different projects from mixing up their libraries. It acts as a clean, fresh space where only your current project's toy bricks are kept.

Section 4 · Process Locks

The Confused Clone Army Bug

Analogy: A master kitchen chef cloning himself to chop carrots, but every clone tries to build a new restaurant.

Once you compile your python script into a standalone desktop application (so you can share it as a double-clickable program with friends), a severe operational system conflict can occur.

To calculate complex machine-learning math fast, background libraries spawn parallel workers (sub-processes) to speed up equations. In a packaged app environment, every spawned background worker tries to re-run your startup script.

Without a process check, every calculation worker thinks: "I am the main program!" and spawns a new web server and opens a new browser tab. Within seconds, your desktop opens hundreds of browser tabs in an endless loop, crashing the operating system.

The Copycat Clone Loop 🤖

Background workers re-execute application startup files. Each worker starts its own web host and spawns new duplicate windows endlessly.

The "Boss Guard" (Process Lock) 🛡️

We query the executing thread name. Only the primary MainProcess is permitted to trigger the browser launch and web server. Workers are blocked!

Section 5 · Desktop Distribution

Shipping Your Toy Box (DMG Installers)

Analogy: Shipping a raw plastic manufacturing facility to your friend vs. shipping a finished castle in a gift-wrapped box.

Your users don't know how to navigate terminals, open command lines, or verify virtual environments. We must package our entire python agent workspace, local assets, and model engines into a single, beautifully wrapped installation package: a DMG disk image.

Standalone App (.app) 📁

A unified macOS bundle directory. It looks like a single executable icon on macOS, but it is actually a nested folder containing the python script, assets, and the local AI runtime.

Installer Disk Image (.dmg) 📦

A virtual disk package. When double-clicked, it mounts on the user's desktop, displaying a clean workspace that directs them to drag the app into their Applications folder.

Section 6 · Datastores

How Local Apps Talk to Central Databases

An elementary look at communication lines: Linking offline calculations with online datastores.

Even though your compiled desktop application runs its AI calculations locally inside the user's laptop memory at $0 recurring cost, how do we synchronize conversation records, swipe directions, and match results back to our global Postgres tables?

The Security Constraint:

Standalone client-side applications should never connect directly to your SQL database. If your packaged `.dmg` app contained your master database connection password, any user could decompile your code, extract your key, and delete your entire database! Clients must talk to databases through intermediate API services.
