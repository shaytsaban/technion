🌉 גשר: JSON מול SQL
שפת ההובלה מול שפת האחסון
SQL = שפת האחסון 🗄️
  • עובדת בתוך מסד הנתונים
  • בין שרתים בלבד
  • לא נשלחת דרך האינטרנט
  • מורצת על ידי השרת — לא הטלפון
JSON = שפת ההובלה 📦
  • עובר בין מכשירים דרך הרשת
  • קריא לכל שפת תכנות
  • מובן לכל מכשיר — iOS, Android, Web
  • מגיע עד לדלת של מסד הנתונים בלבד
JSON הוא משאית ההובלה. SQL הוא המחסן. הם לא מתחרים — הם עובדים בתור.
📌 חיבור לעולם המקצועי

כשתבנה דוח ב-Power BI שמושך נתוני מט"ח חיים מ-API חיצוני — תבין למה ה-dev נותן לך endpoint URL ולא גישה למסד. אם שדה ב-JSON נקרא "exchange_rate" ולא "rate" — הדוח שלך לא יטען.

חזרה למטבח
בפעם הבאה שתלחץ על "הזמן" ב-Wolt — אתה יודע: יצרת JSON זמני → עבר אימות ב-API → הפך ל-INSERT קבוע → הדפיס בצג המטבח.
ההמבורגר הפך לנתון דרך JSON → API → SQL. כל שלב יש לו סיבה ארכיטקטונית. 🍔
🛠️ הכלי האמיתי בתעשייה

Postman — כלי לבדיקת API calls. Power BI → Web Connector — מחבר JSON מ-API ישירות לדשבורד. REST API — הסטנדרט שמשתמש ב-JSON לתקשורת בין שירותים.

💥 מה קורה כשזה נשבר — Dyn DNS Attack, 2016

בנובמבר 2016, ספקית ה-DNS הגדולה Dyn חוותה מתקפת מניעת שירות (DDoS). GitHub, Twitter, Spotify ו-Reddit נפלו במשך שעות — לא כי השרתים שלהם כשלו, אלא כי קריאות ה-API לא הצליחו להגיע אליהם.

ההשפעה על BI: כל דשבורד שמשך נתונים Live מ-API חיצוני הציג מסכים ריקים. אנליסטים שלא הכירו את התלות ב-API לא ידעו אם הבעיה היא בנתונים, בשרת, או ברשת.

API חיצוני = נקודת כשל. תמיד בנה fallback לנתונים מקומיים בדשבורדים קריטיים.
💡 מה לוקחים הביתה
  • SQL = שפת האחסון. JSON = שפת ההובלה. הם לא מתחרים.
  • שרת ה-API מאמת, מסנן ומתרגם JSON ל-SQL לפני שמגיע למסד.
  • בנית BI על API חיצוני? הבן את מבנה ה-JSON — אחרת אתה עיוור לשגיאות.

מה קורה כשאלפי לקוחות קונים את אותו המוצר האחרון בו-זמנית.

🌍 עולם מוכר
מי תפס את כרטיס המסך האחרון? 🎮
אתה ושני שותפים פתחתם חנות מחשבים. ניהלתם מלאי בגוגל שיטס. יש כרטיס NVIDIA RTX 4090 אחרון. בשישי בלילה — שלושה לקוחות מנסים לקנות אותו באותה המילישנייה.

שקף 3 מתוך 7 · תחנה 2
🔬 חשיפה הדרגתית
עקרונות ACID — ארבע ערבויות האמינות
A
Atomicity — אטומיות

הכל או כלום. העברת 500₪ מחשבון א' לב': אם השרת קרס אחרי שהכסף יצא אבל לפני שנכנס — הכסף חוזר לחשבון א'. העסקה כולה מתבטלת (Rollback).

C
Consistency — עקביות

כללי המערכת תמיד נשמרים. קבעת "מלאי לא יכול לרדת מתחת ל-0"? מסד הנתונים יחסום כל עסקה שתנסה לשבור כלל זה — גם אם שגיאת תוכנה מנסה לאפשר זאת.

I
Isolation — בידוד

כל עסקה פועלת כאילו היא היחידה. כשאבי קונה, בני ממתין. כשבני קונה, גלית ממתינה. מנעולים (Locks) על שורות בודדות מבטיחים שאף אחד לא דורס את השני.

D
Durability — עמידות

ברגע שאמרת "הצלחה" — הנתון נכתב פיזית לדיסק. גם אם חשמל נכבה שנייה אחרי — הנתון ישוחזר. לא נשמר ב-RAM בלבד.

📊 מה זה אומר לאנליסט BI
כשדוח ה-BI מציג נתון חלקי
BI מתבסס על נתונים שהמסד התפעולי רשם. אם ACID נכשל (למשל — עסקה התחילה ולא הסתיימה), הדוח שלך יציג נתון חלקי ללא כל אינדיקציה לכך.
⚠️ טעות נפוצה: אנליסט שמבצע UPDATE ישיר על מסד ייצור כדי "לתקן נתון בדשבורד" — שובר את עקביות ה-ACID לחלוטין.
✅ הנוהל הנכון: תיקון נתונים עובר תמיד דרך האפליקציה או ה-ETL — לא דרך SQL ידני על פרודקשן.
לפני שבונים KPI קריטי — בדוק שעמודת is_committed או transaction_status = "success".
שקף 6 מתוך 7 · תחנה 2
🔁 סגירת לולאה
חזרה לכרטיס המסך
כשקנית את הכרטיס האחרון ב-KSP ו"אזל מהמלאי" קפץ לחברך — זה ACID בפעולה. המסד נעל את שורת המלאי, בדק, ואיפשר רק לאחד לקנות.
מנעולים + ACID = הגנה על שלמות הנתונים גם תחת 10,000 משתמשים בו-זמנית. 🔒
🛠️ הכלי האמיתי בתעשייה

pgAdmin — ממשק גרפי ל-PostgreSQL לניטור Transactions. Deadlock = שני תהליכים מחכים זה לזה ואף אחד לא מתקדם — DBA מאבחן בלוגים. BEGIN/COMMIT/ROLLBACK — פקודות SQL לניהול עסקאות ידנית.

💥 מה קורה כשזה נשבר — Bank of America, 2003

בספטמבר 2003, migration שגוי יצר חוסר עקביות בין שני מסדי נתונים. לקוחות ראו משיכות כפולות מחשבונם. הבנק לא קיבל שום התראה אוטומטית על הכשל — רק תלונות לקוחות.

עלות: מאות מיליוני דולרים תיקונים + פגיעה תדמיתית. הסיבה: ACID לא נאכף בין שני מסדים שונים בתהליך ה-migration.

💡 מה לוקחים הביתה
  • ACID = 4 ערבויות: Atomicity, Consistency, Isolation, Durability.
  • מנעולים (Locks) על שורות בודדות מונעים Concurrency conflicts.
  • BI שמציג נתון שגוי = ייתכן שעסקה לא הושלמה. בדוק transaction_status לפני בניית KPI.

🔬 OLTP מול OLAP
שני עולמות שונים לחלוטין
🏃 OLTP
Online Transaction Processing
  • 🎯רישום הזמנות, עסקאות, עדכונים בזמן אמת
  • ⚡קצב: אלפי שורות בשנייה
  • 📏שאילתה: שורה בודדת → מהיר מאוד
  • 👥משרת: לקוחות חיים באפליקציה
  • 🗄️דוגמאות: PostgreSQL, MySQL, SQL Server
  • ⛔סכנה: שאילתה כבדה = קריסת אפליקציה
📊 OLAP
Online Analytical Processing
  • 🎯דוחות, ניתוחים, מגמות היסטוריות
  • 🐢קצב: מיליוני שורות → שניות
  • 📊שאילתה: עמודות שלמות → מאוד כבד
  • 👔משרת: מנהלים, אנליסטים, דשבורדים
  • ❄️דוגמאות: Snowflake, BigQuery, Redshift
  • ✅כוח על: אחסון עמודתי → שאילתות מהירות
אנלוגיה: פנקס הזמנות של מלצר (OLTP) מול ספר החשבונות השנתי (OLAP). אל תחשב רווח שנתי בתוך פנקס ההזמנות החי! 📔

🔬 ETL — Extract, Transform, Load
צינור הנפט הטכנולוגי — 3 שלבים
⛏️
Extract — חילוץ

שליפה עדינה של נתונים חדשים מה-OLTP (בדרך כלל בלילה, כשעומס נמוך). לא שואבים הכל — רק מה שהשתנה מאז הפעם הקודמת (WHERE updated_at > last_run).

⚙️
Transform — התמרה

ניקוי, סנכרון, חישוב. כל הלוגיקה העסקית מבוצעת כאן: המרת מטבע, מחיקת כפילויות, ערכי NULL. זה המח של ה-ETL.

📥
Load — טעינה

הנתון הנקי נכתב למחסן הנתונים (Snowflake/BigQuery) בפורמט עמודתי (Columnar) המותאם לשאילתות אנליטיות מהירות.

אנלוגיה: מפעל מיחזור. אוספים בקבוקים (Extract) → שוטפים וממיינים (Transform) → מסדרים בארגזים (Load). 🏭
שקף 3 מתוך 7 · תחנה 5
💻 Transform בפועל — קוד SQL
שלוש טרנספורמציות נפוצות

1️⃣ המרת מטבע — הכל לדולר

SELECT order_id,
  CASE WHEN currency = 'ILS' THEN amount / 3.7
       WHEN currency = 'EUR' THEN amount * 1.08
       ELSE amount END AS amount_usd
FROM staging_orders;
-- בלי זה: סיכום הכנסות גלובלי חסר כל משמעות

2️⃣ מחיקת כפילויות (Deduplication)

SELECT order_id, customer_id, amount
FROM (
  SELECT *,
    ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY updated_at DESC) AS rn
  FROM staging_orders
) t WHERE rn = 1;
-- שומרים רק את הגרסה האחרונה של כל הזמנה

3️⃣ טיפול בערכי NULL

SELECT
  order_id,
  COALESCE(notes, 'אין הערות') AS clean_notes,
  COALESCE(delivery_time_min, 30) AS delivery_time -- ברירת מחדל 30 דקות
FROM staging_orders;
-- NULL בעמודת מספר = חישובי ממוצע שבורים

🔵 Row Storage (OLTP)

נתונים שמורים שורה-שורה. כדי לחשב ממוצע מחירים — חייבים לקרוא גם שם לקוח, כתובת, טלפון... בזבוז ענק.

🟢 Columnar Storage (DW)

כל עמודה שמורה בנפרד. חישוב ממוצע מחירים = קריאת עמודת מחיר בלבד. מגה-בייטים במקום גיגה-בייטים.

Columnar Storage = קריאת עמודת מחיר בלבד, מבלי לגעת בשם/כתובת/טלפון. מהיר פי 1000 לשאילתות BI. ⚡

📈 מתי כל ארכיטקטורה מתאימה?

שקף 6 מתוך 7 · תחנה 5
📊 מה זה אומר לאנליסט BI
הנתונים שלך לא בזמן אמת — וזה בסדר
כשעובדים מול Snowflake ב-Power BI — הנתונים הם עד לשעת ה-ETL האחרונה. ETL רץ בלילה = הנתונים מעודכנים עד אתמול. אנליסט שלא יודע זאת יציג "Live Dashboard" שמציג נתונים מלפני 8 שעות.
⚠️ לפני שבונה מדד ב-Power BI: בדוק האם ה-ETL כבר חישב אותו. customer_lifetime_value, churn_rate — לרוב כבר מחושבים ב-Transform. כפל חישוב = חוסר עקביות בין דוחות.
✅ כשדוח מציג NULL: כנראה שגיאה ב-Transform של ה-ETL. הנתון לא הגיע למחסן. בדוק לוגים של dbt/Airflow לפני שמאשים את ה-SQL שלך.
🛠️ הכלי האמיתי בתעשייה

dbt (data build tool) — כתיבת Transform כ-SQL מוגדר גרסאות. Apache Airflow — תזמון ותזמורת של ETL pipeline. Snowflake / BigQuery — DW ב-cloud. Power BI → Snowflake connector — חיבור ישיר ל-DW.

💥 מה קורה כשזה נשבר — Starbucks, 2019

שני ETL pipeline שונים מילאו את אותו DW עם לוגיקת Transform שונה לאותה עמודת הכנסות. שני צוותים בנו דוחות שחישבו "Revenue" אחרת. מנהלים קיבלו מספרים סותרים בישיבת דירקטוריון. חקירה של חודשיים לזהות את הכשל.

💡 מה לוקחים הביתה
  • ETL = Extract (שאיבה) → Transform (ניקוי/חישוב) → Load (טעינה ל-DW).
  • Columnar Storage = קריאת עמודה בלבד → פי 1000 מהיר לשאילתות BI.
  • נתונים ב-DW = עד שעת ה-ETL האחרונה. תמיד תוודא רעינות נתונים.

💡 מה לוקחים הביתה
  • LLM מקבל Schema בלבד — לא נתונים. כך שומרים על פרטיות.
  • SQL שנוצר על ידי AI = תמיד לאמת לפני הצגה.
  • Copilot = ייעול. לא תחליף לידע SQL ולהבנת ארכיטקטורה.
