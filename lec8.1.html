מפו דרישה לעמודי התווך

נתונה הדרישה: "המערכת ממליצה למשתמש על פרופילים מתאימים". באילו מארבעת עמודי התווך היא נוגעת? כתבו את כל אלה שעולים בדעתכם, ולמה.

✓ תשובה לדוגמה

הדרישה נוגעת בלפחות שלושה עמודים: מודל נתונים (צריך טבלאות users, preferences, likes כדי לדעת למי להמליץ), שילוב AI (מנוע ההמלצה עצמו), ומערך BI (נמדוד אם ההמלצות מצליחות — שיעור התאמות מתוך המלצות). ניהול הפרויקט יחליט אם זה ב-MVP או ב-v2. זו בדיוק העקיבות: דרישה אחת — חוט שעובר בכל השכבות.

מהי מטרת ההקאתון עצמו?

בשש שעות לא תסיימו מערכת מסחרית. המטרה ריאלית וחדה: להגדיר את הפרויקט באופן קוהרנטי וניתן-למעקב, ולהעמיד פרוסה דקה אחת שעובדת מקצה לקצה. שלד חזק שתבשרו עליו בהמשך — תוכנית אדריכלית מצוינת עם חדר אחד בנוי ומרוהט.

✦למה מגדירים היקף מראש?

כמו שלמדנו ב-Use Case — חלק מהניתוח הוא הגדרת גבולות: מה בפנים (scope) ומה בחוץ. הגדרה מוקדמת מונעת זליגת דרישות ומבטיחה שבסוף היום יהיה תוצר שלם וקטן — ולא חצי-תוצר גדול.

שיטת הליבון — בדיוק כפי שלמדנו: מתחילים מהאפיון העסקי

אל תתחילו מטבלאות. תתחילו מטקסט בעברית שמתאר: מי המשתמשים, מה הם יכולים לעשות, ואילו חוקים יש במערכת. מתוכו מזהים ישויות — שמות העצם שחוזרים. הכלל שלמדנו: אם אפשר לשאול "כמה יש?" או "מה הפרטים של...?" — זו כנראה ישות (וכנראה גם טבלה).

אתם
הפרומפט שלכם (תבנית 4 חלקים)
הקשר: אני בונה את MatchMe. אפיון: "משתמש נרשם, יוצר פרופיל עם ביו ותמונה, מדפדף בפרופילים באותה עיר, עושה Like או דילוג. שני Likes הדדיים = Match ואז אפשר לשלוח הודעות." משימה: זהה ישויות, 3–5 שדות לכל אחת, וסוג הקשר בין כל זוג. אילוצים: רק מה שנרמז באפיון; ציין קשר N:M אם קיים. פורמט: טבלה + רשימת קשרים, בעברית.
AI
תשובת ה-AI
ישויות: users (id, name, email, city, age) · profiles (id, user_id, bio, photo_url) · likes (id, from_user_id, to_user_id, liked_at) · matches (id, user1_id, user2_id, matched_at).
קשרים: user–profile = 1:1 · user–likes = 1:N · user ↔ user דרך likes = N:M (טבלת קישור) · match נגזר משני Likes הדדיים.
✦ביקורת הארכיטקט: ה-AI הציע גם את matches, אף ש"התאמה" נרמזה רק בעקיפין — והוא צדק. אבל זה בדיוק המקום לעצור ולוודא: האם כל ישות שהוא הציע באמת נובעת מהאפיון שלכם? אתם מאשרים, לא הוא.

עכשיו תורכם — על תחום חדש לגמרי, כדי שתתרגלו את החשיבה ולא רק תעתיקו את MatchMe.

מודל נתונים: ERD → טבלאות → SQL

2:45–4:00

זו התחנה הטכנית הגדולה — בונים את "הזיכרון" של המערכת. נלך בדיוק לפי המסלול שלמדנו: מזהים ישויות, מציירים מפה (ERD), הופכים אותה לטבלאות, וממלאים בנתוני דמה.

מושגישות (Entity)

דבר שצריך לשמור עליו מידע — שם עצם שחוזר באפיון. אם אפשר לשאול "כמה יש?" — זו כנראה ישות.

מושגקשר (Relationship)

איך שתי ישויות מתחברות, וכמה מכל צד: 1:1 (לכל אחד אחד), 1:N (לאחד יש הרבה), N:M (הרבה מול הרבה).

מושגטבלת קישור

טבלה שמחברת שתי ישויות ביחס רבים-לרבים. כמו טבלת likes שמחברת משתמש למשתמש.

מושגERD

Entity-Relationship Diagram — מפה ויזואלית של הטבלאות והקווים ביניהן. ציור, לא קוד. מפת עיר לפני בנייה.

מושגמפתח ראשי / זר

Primary Key = מספר ייחודי לכל שורה (כמו ת"ז). Foreign Key = שדה שמצביע על שורה בטבלה אחרת ("שייך ל...").

מושגנרמול (Normalization)

לא לשמור את אותו מידע פעמיים — כל עובדה במקום אחד בלבד. שם של עיר נשמר פעם אחת, ולא בכל שורה.

שני מושגים נוספים: תרשים מחלקות (Class Diagram) — דומה ל-ERD אך מתאר את הישויות העסקיות, התכונות והקשרים העיקריים (אפשר להפיק מ-AI עם PlantUML, שפה טקסטואלית שממנה נוצר תרשים); ונתוני סימולציה — נתוני דמה רבים שתכניסו לטבלאות, כדי שיהיה מה להציג בדשבורד ומה לבדוק.

הדגמה תיעדוף משימות פיתוח · מ-ERD ל-SQL

// תשובת ה-AI — טבלת המשימות (לאחר אישור הארכיטקט) CREATE TABLE tasks (
  id         SERIAL PRIMARY KEY,  -- מספר רץ ייחודי
  title      TEXT NOT NULL,
  project_id  INTEGER REFERENCES projects(id),  -- מפתח זר
  assignee_id INTEGER REFERENCES developers(id),
  priority    INTEGER DEFAULT 3,
  status      TEXT DEFAULT 'open',
  created_at  TIMESTAMP DEFAULT NOW()
);

בפשטות: SERIAL PRIMARY KEY = מספר ייחודי שנוצר אוטומטית. REFERENCES = "השדה הזה חייב להצביע על שורה קיימת בטבלה אחרת" (מפתח זר). DEFAULT = ערך ברירת מחדל אם לא נכתב אחר.

עכשיו אתם

ישויות + קשר מרכזי + טבלת קישור

רשמו את הישויות שלכם, סמנו את הקשר המרכזי (במיוחד אם הוא N:M), ותארו (או בקשו מ-AI ובדקו) את טבלת הקישור.

✓ תשובה לדוגמה — ניהול אירועים מקצה-לקצה

ישויות: events · guests · vendors · tasks. קשרים מרכזיים: אורח ↔ אירוע = N:M (אורח מוזמן לכמה אירועים, אירוע מארח כמה אורחים) → טבלת קישור event_guests; וכן ספק ↔ אירוע = N:M → event_vendors. שימו לב — זו אותה תבנית של טבלת קישור שראינו, פשוט בתחום אחר.

נתוני סימולציה — תנו לדשבורד מה להציג

טבלה ריקה = דשבורד ריק. בקשו מ-AI לייצר הרבה רשומות דמה ריאליסטיות. הנה פרומפט מוכן (כאן בהקשר תחזוקת חירום):

❯ פרומפט · נתוני סימולציה
הקשרמערכת תחזוקת חירום. יש לי טבלאות: assets(id,name), sensors(id,asset_id), readings(id,sensor_id,value,reading_at).

אילוציםPostgreSQL תקין; תאריכים אמיתיים; פיזור הגיוני של ערכים; אל תמציא עמודות שלא קיימות.
פורמטבלוק SQL אחד מוכן להרצה.
iהכינו כבר את שאילתות הדשבורד

בעוד התחנה הבאה תציג דשבורד — השאילתות שמזינות אותו נכתבות כאן. לדוגמה, למערכת המשימות: "כמה משימות פתוחות לכל מפתח" היא בדיוק JOIN + GROUP BY שלמדנו. הריצו אותה עכשיו על נתוני הסימולציה.

// שאילתה שתזין את הדשבורד — משימות פתוחות לכל מפתח SELECT d.name, COUNT(*) AS open_tasks
FROM tasks t
JOIN developers d ON d.id = t.assignee_id
WHERE t.status = 'open'
GROUP BY d.name
ORDER BY open_tasks DESC;
⚠שני פחים: מעט רשומות, ו-JOIN בלי ON

ראשית — מעט רשומות יותירו דשבורד ריק; הקפידו על מספר משמעותי בכל טבלה. שנית — JOIN בלי תנאי ON יוצר מכפלה קרטזית: כל שורה מוכפלת בכל שורה, ומקבלים אלפי שורות שגויות. כל JOIN חייב ON.

מושגסוכן AI (Agent)

רכיב AI שמבצע משימה מוגדרת בתהליך: יש לו תפקיד (Persona), משימות, ונקודות ממשק עם המערכת.

מושגFallback

תוכנית ב' אם שירות ה-AI נופל או מחזיר תשובה שגויה. מה המערכת עושה כשה-AI לא זמין.

מושגLatency (זמן המתנה)

הזמן עד שמקבלים תשובה מה-AI. אם זה לוקח 4 שניות — אסור להקפיא את המסך; מציגים "טוען…".

מושגAPI מול MCP

API = הקוד שלכם פונה ל-AI ("כתוב לי..."). MCP = ה-AI ניגש בחזרה אל הכלים והנתונים שלכם, בצורה מבוקרת.

מסך אחד שמרכז את המספרים החשובים. למנהל — מדדים אסטרטגיים; למשתמש — מידע אישי על פעילותו.

ועוד מושג שכבר פגשנו: הזיה (Hallucination) — כש-ה-AI ממציא משהו בביטחון מלא. בגלל זה כל סוכן צריך Fallback. ניתוח עלות-תועלת פירושו לבחור מודל לפי הצורך: מודל קטן/מהיר/זול (כמו מודל מקומי ב-Ollama) לעומת מודל גדול/חזק/יקר (כמו בענן) — לא תמיד צריך את החזק ביותר.

בוצע = 2–4 פרסונות מבוססות (לא משאלת לב) + פילוח קהל + מסלול משתמש (User Flow) אחד לפחות.

5דרישות לקוח (User Stories)

בוצע = 5–8 User Stories מתועדפות, כל אחת עם קריטריון קבלה בינארי (עובר/נכשל).

6Use Cases

בוצע = 2–3 תרחישים עם שחקן, טריגר, תנאי קדם, מסלול ראשי (Happy Path) ומקרה חריג אחד לפחות.

7דרישות לא-פונקציונליות (NFR)

בוצע = דרישות איכות מדידות במספרים (מהירות, אבטחה, אמינות) — לא "מהיר" אלא "תוך 2 שניות".

8מסכים ו-UX

בוצע = Wireframes למסכים מרכזיים, וכל מסך מחובר לדרישה (תחילת טבלת העקיבות).

9מודל נתונים

בוצע = ERD + פקודות CREATE TABLE עם מפתחות וסוגי נתונים + נתוני סימולציה רבים + שאילתות לדשבורד.

10מדדי הצלחה ודשבורד

בוצע = KPIs קשורים לחזון + דשבורד מנהל + דשבורד משתמש קצה.

11ניהול פרויקט

בוצע = הגדרת MVP + Backlog מתועדף + Roadmap ל-2 גרסאות + כלי ניהול מנומק (Jira/Monday/Asana).

12סיכונים

בוצע = טבלת סיכונים (חומרה × סבירות) עם פעולות מניעה נפרדות מתגובה, בדגש AI/פרטיות/אבטחה.

13שילוב AI

בוצע = סוכן עם Persona ומשימה, מיקום (פרוצדורה/שירות), Fallback מפורש, התייחסות ל-Latency, וניתוח עלות-תועלת.

14אב-טיפוס

בוצע = תרשים ארכיטקטורה + פרוסה אנכית חיה (מסך→API→DB) + שורת מיפוי עקיבות + בדיקת Playwright אחת עם מזהה.

מטריצת העקיבות — מקצה לקצה

זו טבלת הליבה של המסמך כולו: חוט אחד שעובר מהחזון ועד הבדיקה. מלאו לפחות שורה אחת מלאה. כל תא חייב להתחבר לתא שלפניו — אם משהו "מרחף" בלי מקור, זו נורת אזהרה.

בקרת "3 הפחים" — לכל תוצר של AI

לפני שמכניסים תוצר שה-AI יצר (SQL, טקסט, קוד) למסמך — העבירו אותו דרך שלוש הבדיקות האלה. סמנו "בדקתי" לכל אחת.

1 · הזיות (Hallucinations)

האם כל עובדה, פונקציה ושם-טבלה שה-AI כתב — באמת קיימים ונכונים?

הריצו את ה-SQL בפועל מול בסיס הנתונים. ודאו ששמות הטבלאות והעמודות תואמים את ה-CREATE TABLE שלכם. חפשו פונקציות שה-AI "המציא" — אם אתם לא מכירים אותה, בדקו שהיא קיימת לפני שאתם סומכים עליה.
2 · קונטקסט חסר

האם נתתי ל-AI את האפיון, הסכמה והדרישות שלי — או ביקשתי "באוויר"?

לפני שמבקשים שאילתה — הדביקו את ה-CREATE TABLE שלכם לפרומפט. לפני שמבקשים User Story — הדביקו את האפיון. ה-AI לא יודע מה לא סיפרתם לו; קונטקסט חסר = תשובה כללית ולא מתאימה.
3 · "מסכים יותר מדי"

האם ביקשתי מה-AI לחלוק עליי וביקרתי את תשובתו — או רק קיבלתי אישור?

בקשו במפורש: "שחק פרקליט השטן", "היכן אני טועה?". אם ה-AI רק מהלל את מה שעשיתם — לא ביקשתם נכון. הביקורת בעלת הערך מגיעה כשנותנים לו רשות לא להסכים. אתם הארכיטקטים — אתם מאשרים, לא הוא.

בחנו את עצמכם

שש שאלות מהירות על העקרונות המרכזיים. בחרו תשובה — תקבלו משוב מיידי והסבר.

Q1מתי משתמשים בטבלת קישור?
קשר רבים-לרבים לא יכול לשבת בטבלה אחת — צריך טבלה שלישית שמחברת, כמו likes או event_guests.
Q2איזה מהבאים הוא קריטריון קבלה תקין?
קריטריון קבלה חייב להיות בינארי ומדיד — אפשר לענות עליו בבירור "עבר" או "נכשל". השאר הם תחושות, לא מבחנים.
Q3מהו "הכלל הזהב" שמחבר Use Case למודל הנתונים?
"המשתמש מחובר" → שדה session. "הערוץ מחובר" → טבלת channels. כך תנאי הקדם הופכים למבנה נתונים — וזו העקיבות.
Q4מה קורה כש-JOIN נכתב בלי תנאי ON?
בלי ON, בסיס הנתונים מחבר כל שורה בטבלה אחת עם כל שורה בשנייה — ומקבלים אלפי שורות שגויות. כל JOIN חייב תנאי.
Q5מה ההבדל בין API ל-MCP?
ב-API אתם יוזמים את הפנייה אל המודל. ב-MCP נותנים למודל גישה מבוקרת חזרה אל הכלים והנתונים שלכם.
Q6מהו תפקיד ה-Fallback בסוכן AI?
במערכת אמיתית, תשובה שגויה לרוב גרועה מאין-תשובה. ה-Fallback מגדיר מה קורה כשה-AI לא זמין או לא בטוח — למשל מעבר לפעולה ידנית.
