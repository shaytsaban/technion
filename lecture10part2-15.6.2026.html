מילון המושגים — לפני שמתחילים

כל מונח שיופיע בהרצאה — עם הגדרה ברורה, דוגמה חזותית, ומה הוא אומר לאנליסט.

🗂️ מושג 1 — SQL מול NoSQL
שני עולמות של מסדי נתונים — מה ההבדל?
SQL = Structured Query Language. מסד נתונים שבו כל הנתונים מאורגנים בטבלאות, ממש כמו Excel — שורות ועמודות. לכל עמודה יש שם וסוג נתון קבוע מראש. זה נקרא Relational Database.
NoSQL = "לא רק SQL". מסד שבו הנתונים לא חייבים להיות בטבלה — הם יכולים להיות בפורמטים גמישים: JSON, מסמכים, גרפים, Key-Value.
🔵 SQL — דוגמה חיה: טבלת הזמנות
order_idcustomeritemprice
1001ישראלהמבורגר52
1002שרהפיצה78
1003ישראלסלט38
✅ מבנה קבוע — כל הזמנה חייבת order_id, customer, item, price
🟢 NoSQL (MongoDB) — אותה הזמנה כ-JSON

✅ מבנה גמיש — כל הזמנה יכולה להכיל שדות שונים
מתי בוחרים SQL? כשיש מבנה קבוע וברור, נדרשות שאילתות מורכבות (JOIN בין טבלאות), ויש צורך בגיבוי עסקאות (ACID). מתי בוחרים NoSQL? כשהנתון משתנה לעיתים קרובות, כשנדרשת מדרגיות גבוהה מאוד, או כשהנתון "לא מרובע" (כמו פרופיל משתמש עם שדות שונים לכל אחד).
קריטריוןSQL (Relational)NoSQL
מבנה נתוניםטבלאות קבועות (Schema נוקשה)מסמכים/JSON גמישים
שאילתותSQL — שפה אחת לכולםAPI שונה לכל מסד
ACID✅ מלא — בנוי מהיסוד⚠️ חלקי — תלוי במוצר
JOIN בין טבלאות✅ קל ומהיר❌ קשה — אין מנגנון JOIN מובנה
מדרגיות (Scale)⚠️ קשה להרחיב אופקית✅ מיועד להרחבה ל-millions
דוגמאות נפוצותPostgreSQL, MySQL, SQL ServerMongoDB, Redis, Cassandra, DynamoDB
שימוש ב-BI✅ ישיר — BI tools בנויים לSQL⚠️ דרוש תרגום/ETL לפני BI
כלל אצבע: הזמנות, מכירות, לקוחות → SQL. פרופילי משתמשים, logs, תוכן גמיש → NoSQL. רוב הארגונים משתמשים בשניהם. 🔀
🔗 איפה זה מופיע בהרצאה

ב-OLTP (תחנה 4 חלק א) — PostgreSQL = SQL. ב-Data Lake (תחנה 7) — JSON מ-MongoDB = NoSQL. ב-Kafka (תחנה 8) — events = JSON = NoSQL בתעבורה. ב-ETL (תחנה 5 חלק א) — Transform = המרת NoSQL ל-SQL לפני ה-DW.

📋 מושג 2 — מטא-דאטה
מטא-דאטה — "נתונים על נתונים"
מטא-דאטה הוא מידע שמתאר נתון אחר — לא הנתון עצמו. אנלוגיה: ספר בספרייה. הנתון = תוכן הספר. המטא-דאטה = שם המחבר, מספר עמודים, תאריך הוצאה, ז'אנר, מיקום על המדף.
הנתון עצמו (בטבלת הזמנות)

ב-Data Catalog (תחנה 9) — כל ה-Catalog הוא מטא-דאטה. הוא לא מכיל שורת הזמנה אחת — הוא מכיל מידע על הטבלאות. ב-Lakehouse (תחנה 7) — Apache Iceberg ו-Delta Lake הם שכבות מטא-דאטה: הם לא מאחסנים את הנתונים, הם מנהלים את "ספר הטלפונים" שמסביר איפה הנתון יושב ב-S3.
מטא-דאטה = "ספר הטלפונים של הנתונים". בלעדיו — יש לך 10TB של קבצים ב-S3 ואי-אפשר למצוא כלום. עמו — כל שאילתה יודעת בדיוק לאן ללכת. 📂
🗜️ מושג 3 — Parquet (ולמה זה לא SQL)
קודם כל: SQL ו-Parquet הם לא אותה קטגוריה
זו הבלבול הכי נפוץ, אז נפרק אותו לאט. דמיין ארון מסמכים:
📁
Parquet = הקובץ עצמו

זה איך הנתונים שמורים על הדיסק. בדיוק כמו .xlsx או .csv — סוג קובץ. אתה לא "מדבר" עם קובץ, אתה רק שומר וקורא אותו.

🗣️
SQL = השפה לבקש נתונים

זה איך אתה מבקש נתונים — "תן לי את כל ההזמנות מתל אביב". SQL לא קובץ, הוא משפט שאתה כותב.

הם לא מתחרים — הם עובדים יחד: אתה כותב SQL (שאלה) כדי לקרוא נתונים שמאוחסנים בקובץ Parquet. כמו שאתה שואל שאלה בעברית על מסמך Word. 🔑
📌 אנלוגיה מדויקת: Parquet = פורמט הקובץ (כמו mp3 לשיר). SQL = הבקשה ("נגן את השיר הזה"). XLSX, CSV, Parquet — כולם פורמטי קבצים. SQL, DAX — כולם שפות בקשה.
🗜️ מושג 3 (המשך) — למה המציאו Parquet
הבעיה ש-Parquet בא לפתור — בדוגמה אחת
נניח שיש לך טבלת הזמנות עם מיליון שורות ו-5 עמודות. מנהל שואל: "מה הסכום הממוצע של כל ההזמנות?" — כלומר, צריך רק את עמודת amount. נראה מה קורה בשתי שיטות אחסון:
❌ שיטה 1 — אחסון שורתי (כמו Excel רגיל ו-CSV)
המחשב שומר את הנתונים שורה-אחר-שורה, כל הערכים של כל שורה ביחד:
מה המחשב קורא מהדיסקמה באמת צריך
1 · ישראל · ת"א · 52 · 2024-01-01רק ה-52
2 · שרה · חיפה · 78 · 2024-01-02רק ה-78
3 · דן · ירושלים · 43 · 2024-01-03רק ה-43
כדי להגיע לעמודת amount, המחשב נאלץ לקרוא הכל — גם שמות, גם ערים, גם תאריכים. 80% מהעבודה מבוזבזת. במיליון שורות = זמן וכסף.
✅ שיטה 2 — אחסון עמודתי (זה מה ש-Parquet עושה)
המחשב שומר כל עמודה בנפרד — כל ה-amount ביחד, כל ה-name ביחד:
איך Parquet שומרמה המחשב קורא
חבילת order_id: [1, 2, 3, ...]⏭️ מדלג
חבילת name: [ישראל, שרה, דן, ...]⏭️ מדלג
חבילת city: [ת"א, חיפה, ירושלים, ...]⏭️ מדלג
חבילת amount: [52, 78, 43, ...]✅ קורא רק את זה!
חבילת date: [2024-01-01, ...]⏭️ מדלג
המחשב ניגש ישר לחבילת amount ומדלג על השאר. קורא 20% מהנתונים → התשובה חוזרת פי 5 מהר יותר. זה כל הקסם של Parquet.
⏸️ עצור וחשוב

למה דווקא שאילתות BI מרוויחות מ-Parquet, אבל אפליקציית Wolt (OLTP) דווקא מעדיפה אחסון שורתי? רמז: כשלקוח פותח הזמנה, הוא צריך את כל השדות של שורה אחת — לא עמודה אחת ממיליון שורות.

🛠️ מושג 3 (תכלס) — מה עושים עם Parquet בפועל
3 דברים שצריך לזכור — וזהו
📦
1. קטן פי 5

CSV של 1GB = Parquet של ~200MB. Parquet דוחס כי כל עמודה מאותו סוג (כל ה-amount מספרים) → קל לדחוס. חוסך עלות אחסון בענן.

⚡
2. מהיר ל-BI

שאילתות שמסכמות עמודה (SUM, AVG, COUNT) רצות פי 5–100 מהר יותר. בדיוק מה ש-BI עושה כל היום.

🚫
3. לא נפתח ב-Excel

Parquet הוא "בינארי" — קוד מכונה, לא טקסט. תנסה לפתוח ב-Notepad → ג'יבריש. אבל Tableau, Power BI ו-Snowflake קוראים אותו ישירות.

בפועל, מתי אנליסט פוגש Parquet? כשה-Data Engineer אומר "הנתונים יושבים ב-S3 בפורמט Parquet". אתה לא יוצר אותו ידנית — הוא נוצר אוטומטית ב-ETL. אתה רק קורא ממנו דרך Tableau/Power BI, או דרך SQL במנוע כמו Athena.

💡 המשפט שצריך לזכור: "כותבים שאלה ב-SQL, הנתונים שמורים בקובץ Parquet, מנוע כמו Athena/Spark קורא את ה-Parquet ומחזיר תשובה." זה הכל.
Parquet = סוג קובץ חכם לנתונים גדולים. עמודתי (קורא רק מה שצריך) + דחוס (פי 5 קטן). SQL = השפה שבה מבקשים. שניהם חברים, לא יריבים. ❄️
🏗️ מושג 4 — שכבת אחסון
מה זה "שכבת אחסון" — ואיך קשור ל-S3
ארכיטקטורת נתונים מורכבת משכבות — כל שכבה אחראית על דבר אחד. "שכבת אחסון" = איפה הנתונים יושבים פיזית.
כשאומרים "שכבת אחסון" — מתכוונים לשורה התחתונה: S3 / Blob / דיסק. הנתונים יושבים שם כקבצים. כל השכבות מעליה בונות על זה. 🏗️
🧊 מושג 5 — Apache Iceberg
Apache Iceberg — "תוכנת ניהול" לקבצים ב-S3
דמיין שיש לך 50,000 קבצי Parquet ב-S3. בלי כלום נוסף — S3 הוא רק "תיקיית קבצים". אי-אפשר לשאול SELECT, אי-אפשר לעדכן, אי-אפשר לדעת מתי כל קובץ עודכן.
Apache Iceberg = שכבת מטא-דאטה שיושבת מעל ה-S3 ומוסיפה לו "יכולות של מסד נתונים" — בלי לשנות את הקבצים עצמם.
❌ S3 לבד:
s3://bucket/orders/part-0001.parquet
s3://bucket/orders/part-0002.parquet
s3://bucket/orders/part-0003.parquet

שאלה: "כמה הזמנות היו בינואר?" = קרא כל 3 קבצים. לא יודע מה בכל קובץ.
✅ Iceberg מעל S3:
Iceberg מנהל "קטלוג" פנימי:
part-0001 = ינואר 2024 (min_date: 1/1, max_date: 31/1)
part-0002 = פברואר 2024
part-0003 = מרץ 2024

שאלה: "כמה הזמנות היו בינואר?" = קרא רק part-0001. 🎯
מה Iceberg מוסיף מעבר לזה:
  • ACID Transactions: שני תהליכי ETL לא יכתבו לאותו קובץ בו-זמנית
  • Time Travel: SELECT * FROM orders AS OF TIMESTAMP '2024-09-01' — חזרה לנתון שהיה בתאריך הזה
  • Schema Evolution: הוספת עמודה חדשה לא "שוברת" את כל הקבצים הישנים
  • Partition Pruning: הנחיה לקריאת קבצים רלוונטיים בלבד
Apache Iceberg = ה"מנהל" של S3. S3 = ספרייה בלי כתובות. Iceberg = ה-Index של הספרייה. 🧊
📐 מושג 6 — DAX
DAX — "הנוסחאות" של Power BI
DAX = Data Analysis Expressions. שפת נוסחאות ייחודית ל-Power BI (ו-Excel Power Pivot). חשוב על DAX כמו VLOOKUP על סטרואידים — במקום לחשב ערך אחד בתא, DAX מחשב מדדים שלמים על מיליוני שורות.
✅ DAX — דוגמאות מהחיים
-- מדד פשוט: סך מכירות
Total Revenue =
  SUM(Orders[amount_ils])

-- מדד עם תנאי: מכירות ספטמבר בלבד
Sep Revenue =
  CALCULATE(
    SUM(Orders[amount]),
    Orders[month] = 9
  )

-- % שינוי מחודש קודם
MoM Change % =
  DIVIDE(
    [Total Revenue] - [Prev Month Rev],
    [Prev Month Rev]
  )

⚠️ DAX שגוי = KPI שגוי בלי Error. Power BI לא מוציא שגיאה — הוא מציג מספר שגוי. תמיד תבדוק תוצאה ביד לפני שמציג.
DAX = "Excel מתקדם בתוך Power BI". מחשב KPIs מורכבים על הנתונים שכבר טעונים. לא מחליף SQL — עובד אחריו. 📐
📦 מושג 7 — JSON מול XML
שני פורמטי "הובלת נתונים" — מה ההבדל?
שני הפורמטים משמשים להעברת נתונים בין מערכות (דרך API, Web Services). שניהם טקסט קריא. ההבדל — עיצוב, גודל, וקלות עיבוד.

⚡ מושג 8 — Query Engine
Spark, Trino, Athena — "המנועים" שמריצים SQL על קבצים
SQL רגיל רץ על מסד נתונים (PostgreSQL, MySQL). אבל נתונים ב-Data Lake יושבים כקבצי Parquet ב-S3 — אין שם מסד נתונים. Query Engine הוא כלי שלוקח שאילתת SQL שלך ו"מתרגם" אותה לקריאת קבצים מ-S3.
⚡ Apache Spark

מנוע עיבוד מבוזר. מחלק שאילתה ל-100 "עובדים" שרצים במקביל. משמש ב-ETL כבד (Transform מיליוני שורות). Databricks בנויה על Spark.

🔍 Trino / AWS Athena

Query Engine ל-ad-hoc queries. כותבים SQL רגיל → Athena מריץ על S3 ישירות. Pay-per-query (לפי כמות נתונים שנסרקו). מהיר ל-BI אנליסטים שרוצים לחקור נתונים.

Query Engine = "מתרגם" שהופך SQL רגיל לקריאת קבצים ב-S3. בלעדיו — Data Lake הוא רק תיקייה. עמו — הוא DW לכל דבר. ⚡
💡 מה לוקחים מהמילון הזה קדימה
  • SQL = טבלאות קבועות + JOIN. NoSQL = מבנה גמיש (JSON/Document). ETL ממיר NoSQL → SQL לפני BI.
  • מטא-דאטה = "נתונים על נתונים". Data Catalog = מטא-דאטה מרכזי של כל ה-DW.
  • Parquet = סוג קובץ (כמו CSV/XLSX). SQL = שפה לבקש נתונים. לא מתחרים — כותבים SQL כדי לקרוא קובץ Parquet.
  • Iceberg = "מנהל" לקבצי Parquet ב-S3. מוסיף ACID, Time Travel, Schema Evolution.
  • DAX = שפת ה-KPI של Power BI. עובד אחרי SQL, לא במקומו.
  • JSON = הסטנדרט המודרני לתקשורת. XML = Legacy Systems. Tableau Public תומך בשניהם.

🔬 Data Lake — השפיכה הגדולה
עיקרון "הכנס הכל — תמיין מאוחר יותר"
Data Lake = מאגר אחסון ענקי (S3/Azure Blob/GCS) שמקבל כל פורמט, ללא Schema מוקדם. הנתון נשאב ונשמר גולמי. הניתוח קורה בעת השאילתה (Schema-on-Read).
🥩 Raw Zone — כל דבר נשמר כמו שהוא: JSON, logs, images, CSV, Parquet
🧹 Cleaned Zone — נוקה, אוחד, כפילויות הוסרו (Schema-on-Read)
✨ Curated Zone — מוכן לניתוח: טבלאות מנורמלות, KPIs מחושבים

שלוש אזורים ב-Data Lake — נתון זורם מלמטה לעד למעלה

אנלוגיה: אגם שמקבל כל זרם — גשמים, נהרות, שלג נמס. לא בוחרים מה נכנס. בוחרים מה שואבים. 🏞️
🔗 חיבור למושגי יסוד (תחנה 0)

ה-Raw Zone מלא ב-NoSQL: JSON מ-Kafka, logs, מסמכים ממונגו, תמונות. ה-Curated Zone = SQL: טבלאות מנורמלות שניתן לחבר לטבלו ו-Power BI. ה-ETL (Transform) הוא שממיר NoSQL → SQL בין שתי השכבות.

📊 מה זה אומר לאנליסט BI
Power BI + Lakehouse — חיבור חדש שדורש הבנה חדשה
בחברות שעברו ל-Lakehouse, הדשבורד שלך מתחבר לטבלאות בפורמט Parquet על S3 — לא לטבלאות SQL קלאסיות. הנתונים שאתה רואה ב-Power BI הם לרוב תוצאות של Spark queries, לא PostgreSQL פשוט.
⚠️ Parquet מול CSV: Parquet = פורמט עמודתי בינארי. לא תוכל לפתוח אותו ב-Excel. כשה-ETL pipeline שולח לך "export", בקש CSV לבדיקה או Parquet ל-Power BI.
🔵 Time Travel ל-BI: אם דוח BI מציג נתון שנראה שגוי — בקש מה-Engineer לבצע Time Travel לגרסה קודמת ולהשוות. זה כמו Ctrl+Z למחסן נתונים.
הארכיטקטורה הזו מחייבת אותך להכיר מושגים כמו partition — חלוקת הנתונים לפי תאריך או מחלקה כדי לזרז שאילתות. שאילתה על orders WHERE year=2024 לא קוראת את כל הנתונים — רק partition של 2024.

Databricks — פלטפורמת Lakehouse מובילה. Delta Lake — שכבת ACID על S3. Apache Iceberg — סטנדרט פתוח למטא-דאטה של Lakehouse (הגדרה מלאה בתחנה 0). Apache Parquet — פורמט אחסון עמודתי בינארי — עמודתי = קריאת עמודות בנפרד, בינארי = קוד מכונה דחוס לא קריא לאדם (הגדרה מלאה בתחנה 0). AWS S3 / Azure ADLS / GCS — שכבת האחסון — איפה הקבצים שוכנים פיזית.

💡 מה לוקחים הביתה
  • DW = מובנה, מהיר, יקר. Lake = גמיש, זול, מסוכן ללא ניהול. Lakehouse = שניהם.
  • Schema-on-Read = גמישות. Schema-on-Write = אכיפה. כל ארגון מחליט לפי צרכיו.
  • Data Swamp = Lake ללא Data Catalog. הנתון קיים — אבל אי-אפשר למצוא אותו.
  • BI אנליסט בחברת Lakehouse עובד מול Parquet + Spark — לא SQL רגיל בלבד.

🔬 Apache Kafka — הסטנדרט
ה"אוטובוס" של הנתונים — כיצד Kafka עובד
Kafka הוא Message Broker — מתווך בין מקורות נתונים לצרכניהם. הוא לא מעבד נתונים — הוא מנתב ושומר אותם בצינורות (Topics) בסדר מוגדר.

📦 פורמט ה-Event ב-Kafka: JSON ≠ XML
כמעט כל event ב-Kafka עובר כ-JSON (ראה תחנה 0). XML כמעט לא נראה ב-Streaming מודרני — הוא כבד מדי ל-throughput של מיליוני events/שנייה. אם מערכת Legacy (SAP, בנק ישן) שולחת XML — ה-ETL Transform ממיר לJSON לפני שמגיע ל-Kafka.

ממשל נתונים (Data Governance) = מסגרת הכללים, התפקידים, והתהליכים שמבטיחים שנתון אחד = הגדרה אחת = מספר אחד בכל הארגון.
לא מדובר בטכנולוגיה — מדובר בתהליך ארגוני. Governance כולל:
  • Data Catalog — אינדקס מה קיים, איפה, ומה המשמעות של כל שדה.
  • Data Stewards — אנשים שאחראיים לאיכות ועדכניות הנתון בתחום שלהם.
  • Business Glossary — הגדרה מוסכמת לכל מונח עסקי: מה זה "הכנסה"? מה זה "לקוח פעיל"?
  • Data Lineage — מאין הגיע הנתון ודרך אילו טרנספורמציות עבר (תחנה 12).
