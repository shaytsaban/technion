שני עולמות — ולמה שניהם חיוניים

העולם הראשון: SQL — שפת הנתונים

SQL (Structured Query Language) היא השפה שמאפשרת לנו לדבר עם מסדי נתונים. למדנו אותה כדרך לשלוף, לסנן, לסכם ולחבר מידע. אבל SQL לבד היא כמו פטיש מבלי שאוחזים בו — כלי עצמתי שחסרה לו כוונה.

💡 מה SQL נותנת לנו:

דיוק מוחלט — נוכל לשלוף בדיוק את הנתונים שצריך, לא יותר ולא פחות.
ביצועים — מסדי נתונים מותאמים לעבוד עם מיליוני שורות ביעילות.
אמינות — מנגנוני ACID מבטיחים שהנתונים יישארו נכונים גם בתנאי כישלון. 

-- דוגמה: שאילתה שלמדנו בהרצאה 2
SELECT
    d.name AS department_name,
    COUNT(e.id) AS employee_count,
    AVG(e.happiness_score) AS avg_happiness,
    COALESCE(SUM(i.cost), 0) AS total_investment
FROM departments d
LEFT JOIN employees e ON d.id = e.dept_id
LEFT JOIN interventions i ON d.id = i.dept_id
GROUP BY d.id, d.name
HAVING AVG(e.happiness_score) < 7
ORDER BY avg_happiness ASC;

זוהי שאילתה שלמדנו לכתוב. אבל מישהו צריך היה להחליט שהשאילתה הזו בכלל נחוצה, מה היא אמורה להחזיר, ובאילו תנאים להריץ אותה. זה בדיוק מה שה-Use Case עושה.

העולם השני: Use Case — שפת הדרישות

Use Case, שלמדתם עם ד"ר רמי רשקוביץ, הוא כלי לתיאור מה מערכת עושה עבור מי, בתנאים מסוימים. הוא לא מדבר על איך המחשב מבצע את הפעולה — הוא מדבר על הערך שהמשתמש מקבל.

💡 מה Use Case נותן לנו:

בהירות עסקית — כולם מבינים מה המערכת צריכה לעשות.
הגדרת גבולות — מה בפנים (scope), מה בחוץ.
תיעוד תרחישים — גם ה"נתיב השמח" וגם מה קורה כשמשתבש.

🌉 אנלוגיה: בניית גשר

Use Case הוא כמו המפרט של הגשר: "הגשר יחבר בין עיר A לעיר B, יעמוד ב-50 טון, ויאפשר מעבר כלי רכב ורוכבי אופניים". המפרט לא אומר בדיוק אילו בריחים להשתמש.

SQL הוא כמו עבודת הנדסה: "נשתמש בקורות פלדה מסוג X, ביסוס Y, ומפרט ריתוך Z". זה האיך שמממש את המה.

🗄️ SQL — "האיך"

  • שליפת נתונים מטבלאות
  • חיבור טבלאות עם JOIN
  • קיבוץ עם GROUP BY
  • סינון עם WHERE / HAVING
  • לוגיקה עסקית עם CASE WHEN
  • עבודה עם תאריכים
  • טיפול ב-NULL עם COALESCE

📋 Use Case — "המה"

  • הגדרת שחקנים (Actors)
  • תיאור תרחיש ראשי (Happy Path)
  • תרחישים חלופיים ושגיאות
  • תנאים מוקדמים ותנאי סיום
  • קשרי include / extend
  • הכללה (Generalize)
  • דרישות מיוחדות (NFR)

Use Case: "דפדוף בפרופילים"

מה שלמדנו עם ד"ר רשקוביץ

שחקן ראשי: משתמש רשום
טריגר: המשתמש בוחר להיכנס למסך דפדוף
תרחיש ראשי: המערכת מאתרת פרופילים מתאימים ומציגה אותם
תנאי קדם: המשתמש מחובר ויש לו פרופיל פעיל

🔍 שאלה קריטית: מה המסד צריך לאחסן כדי שה-Use Case יעבוד?

נחשוב יחד: כדי שהמערכת "תאתר פרופילים מתאימים", היא צריכה לדעת: מי המשתמש, מה ההעדפות שלו, מי קיים במערכת, ומי כבר דולג/חסום. כל אלה — טבלאות במסד הנתונים.

🔢 SQL — "האיך" הטכני

עכשיו אנחנו כותבים שאילתה שממשת את ה-Use Case:
עדכון סטטוס אימות, שאילתת בדיקה, דוח ניהולי — הכל SQL. 

-- SQL שממש את Use Case "אימות זהות"
-- שלב 1: עדכון אחרי אימות מוצלח
UPDATE profiles
SET
    is_verified = TRUE,
    verified_at = CURRENT_TIMESTAMP
WHERE user_id = 42;

-- שלב 2: דוח לצוות התמיכה — כמה אומתו השבוע?
SELECT
    strftime('%Y-%W', verified_at) AS week,
    COUNT(*) AS verifications
FROM profiles
WHERE is_verified = TRUE
GROUP BY week
ORDER BY week DESC;

שאלה 4 — מה-Use Case למסד

ב-Use Case "דפדוף בפרופילים", אחד הכללים העסקיים הוא: "לא יוצגו פרופילים שהמשתמש חסם".

כיצד הכלל הזה יבוא לידי ביטוי בשאילתת SQL?

א
בתנאי WHERE is_blocked = FALSE בטבלת users
ב
בתנאי WHERE u.id NOT IN (SELECT blocked_id FROM blocks WHERE blocker_id = ?)
ג
זה לא עניין של SQL — רק של הממשק
ד
בפרמטר LIMIT 0
יש לנו טבלת blocks נפרדת. כדי לסנן, נשתמש ב-NOT IN עם subquery, או LEFT JOIN עם IS NULL. זה בדיוק מה שלמדנו בפרק ה-JOIN!

ה-Use Case "קבלת התאמה" — מבט טכני

בואו נראה את Use Case שלמדתם דרך עיניים של מנהל נתונים:

📋 Use Case: קבלת התאמה — ה"מה" מול ה"איך"
טריגר
המשתמש מבצע Like → INSERT INTO likes (from_user_id, to_user_id, liked_at) VALUES (?, ?, NOW())
בדיקת Like הדדי
SELECT id FROM likes WHERE from_user_id = ? AND to_user_id = ? — אם מחזיר שורה: יש התאמה!
יצירת Match
INSERT INTO matches (user1_id, user2_id, matched_at, is_active) VALUES (?, ?, NOW(), TRUE)
תנאי כישלון — חסום
בדיקה קודמת: SELECT 1 FROM blocks WHERE blocker_id IN (?, ?) AND blocked_id IN (?, ?)
תנאי כישלון — כבר קיים
SELECT 1 FROM matches WHERE is_active = TRUE AND ((user1_id=? AND user2_id=?) OR (user1_id=? AND user2_id=?))

CREATE INDEX idx_likes_from_to ON likes(from_user_id, to_user_id) — הדרישה המיוחדת הופכת לאינדקס

🏢 EHI — מבט חדש על מסד מוכר

אתם כבר מכירים את EHI — עכשיו תבינו אותו

לאורך הרצאות 1 ו-2 עבדנו עם מסד הנתונים של EHI (Employee Happiness Investments). כתבנו JOINs, GROUP BY, CASE WHEN ועוד. אבל מי ניסח את השאילתות האלה? ולמה דווקא כאלה?

עכשיו נשחזר את ה-Use Cases שמאחורי כל שאילתה שכתבנו. זה יחזק את ההבנה שלכם ב-SQL — כי תדעו למה כל שורה קיימת.

💡 ה-EHI Database — הסיפור

EHI היא חברה שמשקיעה באושר עובדים. יש לה מחלקות, עובדים בכל מחלקה, וסוגי התערבויות (חדר כושר, עיסויים, סדנאות) שהיא מממנת. כל שאילתה שכתבנו מגיעה ממישהו שישב בישיבה ואמר: "אני רוצה לדעת..."

# Use Case (מה?) שחקן ראשי SQL שלמדנו פרק

ניתוח Use Case עמוק: UC-5 — "דירוג רמת סיכון"

בואו ניצור Use Case מלא לשאילתה שכתבנו בפרק 3:

📋 מפרט Use Case מלא: EHI-UC-5 — דירוג רמת סיכון לעובדים
שם
דירוג עובדים לפי רמת סיכון לאושר נמוך
מטרה
לאפשר ליועץ האושר לזהות עובדים הזקוקים להתערבות דחופה, לפי ציון האושר שלהם
שחקן ראשי
יועץ אושר (Happiness Consultant)
טריגר
ישיבה רבעונית של צוות ה-HR
תנאי קדם
קיימות שורות בטבלת employees עם ציון happiness_score
תרחיש ראשי
1. יועץ מפעיל דוח → 2. מערכת שולפת עובדים → 3. CASE WHEN מדרג לסיכון גבוה/בינוני/נמוך → 4. הדוח מוצג ממוין
תרחיש חלופי
אם happiness_score = NULL → COALESCE מחזיר 0 → הדירוג "סיכון גבוה"
SQL שממש זאת
SELECT name, CASE WHEN happiness_score >= 8 THEN 'נמוך' WHEN happiness_score >= 5 THEN 'בינוני' ELSE 'גבוה' END AS risk_level FROM employees ORDER BY happiness_score ASC
-- EHI-UC-5: דירוג רמת סיכון לעובדים
SELECT
    e.name,
    d.name AS department,
    COALESCE(e.happiness_score, 0) AS score,
    CASE
        WHEN COALESCE(e.happiness_score, 0) >= 8 THEN '✅ סיכון נמוך'
        WHEN COALESCE(e.happiness_score, 0) >= 5 THEN '⚠️ סיכון בינוני'
        ELSE '🚨 סיכון גבוה'
    END AS risk_level
FROM employees e
JOIN departments d ON e.dept_id = d.id
ORDER BY score ASC;

שאלה 6 — EHI Use Case לשאילתה

מנהל כספים של EHI אמר: "תראה לי את ההוצאה החודשית על התערבויות — רק עבור חודשי 2026 — ורק עבור מחלקות שהוצאו בהן יותר מ-1000 שקל בחודש."

איזה Use Case רכיב SQL ייצג את "רק עבור מחלקות שהוצאו בהן יותר מ-1000"?

א
WHERE cost > 1000
ב
HAVING SUM(cost) > 1000 — כי זה סינון לאחר GROUP BY
ג
LIMIT 1000
ד
CASE WHEN cost > 1000 THEN 'include'
כשמסנן לפי ערך מצרפי (SUM, AVG, COUNT) — תמיד HAVING, לא WHERE. WHERE פועל לפני הקיבוץ, HAVING לאחריו.
