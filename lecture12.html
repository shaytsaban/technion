Stored Procedures — "מתכונים שמורים" במסד

איך לשמור פעולה מורכבת פעם אחת בתוך המסד, ולקרוא לה בשם — במקום לחזור עליה כל פעם מחדש.

🧠 קודם כל — מה זה בכלל? (בשפה של בן אדם)

Stored Procedure (בעברית: "פרוצדורה שמורה") היא סדרה של פקודות SQL ששומרים בתוך מסד הנתונים עצמו, נותנים לה שם, וקוראים לה בשם מתי שצריך. במקום לשלוח כל פעם מחדש את כל הפקודות — שולחים שורה אחת: "תריץ את הפרוצדורה ששמה כך-וכך".

🤔 רגע אחד — למה בכלל צריך כמה פקודות SQL להזמנה אחת?

בלי לענות על זה אי אפשר להבין את היתרון, אז נלך לאט. זוכרים מחלק ב׳-1 שהמידע מפוזר ב-4 טבלאות נפרדות (נורמליזציה)? בגלל זה, הזמנה אחת "פשוטה" של יוסי דורשת בעצם כמה פעולות נפרדות במסד:

SQL · הזמנה אחת = 4 פקודות נפרדות
-- 1. check there is enough stock
SELECT stock FROM products WHERE product_id = 7;
-- 2. open a new order row
INSERT INTO orders (...) VALUES (...);
-- 3. add the ordered item to that order
INSERT INTO order_items (...) VALUES (...);
-- 4. reduce the stock by what was bought
UPDATE products SET stock = stock - 3 WHERE ...;

זה הרבה — וגם מסוכן: אם האפליקציה תשכח את שלב 4, המלאי לא יתעדכן והנתונים "ישקרו". הפתרון: לארוז את כל 4 השלבים כ"מתכון" אחד בתוך המסד, ולקרוא לו בשם.

🍳 האנלוגיה: מתכון במטבח

בלי מתכון שמור — בכל פעם שמישהו רוצה עוגה אתם מכתיבים מההתחלה: "קח קמח, 3 ביצים, ערבב, אפה ב-180°"... שוב ושוב. עם מתכון שמור אתם אומרים רק: "תכין עוגה מס' 7" — והמטבח יודע את כל הצעדים.

אצלנו: במקום 4 פקודות, האפליקציה שולחת שורה אחת — CALL place_order(...) — והמסד מריץ את כל 4 הצעדים בעצמו.

יבגני מבהיר נקודה שמבלבלת רבים: זה לא קשור ל-OLAP מול OLTP! פרוצדורה היא כלי בתוך המסד התפעולי (OLTP) — היא עוזרת לבצע פעולות. ההבחנה OLTP/OLAP היא "איפה הנתונים יושבים ולמה" (תפעול מול ניתוח), ופרוצדורה היא "איך מבצעים פעולה" בתוך ה-OLTP. שני נושאים שונים לגמרי.

    -- create a table to store customers:
CREATE TABLE customers (
  -- auto-numbered unique id for each customer
  customer_id SERIAL PRIMARY KEY,
  -- the customer's name (NOT NULL = cannot be empty)
  name        TEXT NOT NULL,
  -- email address; UNIQUE = no two customers can share one
  email       TEXT UNIQUE
);
-- create a table to store products:
CREATE TABLE products (
  -- auto-numbered unique id for each product
  product_id SERIAL PRIMARY KEY,
  -- the product's name
  name       TEXT NOT NULL,
  -- price with 2 decimals, e.g. 49.90
  price      NUMERIC(10,2) NOT NULL,
  -- how many units are in stock (DEFAULT 0 if not given)
  stock      INTEGER NOT NULL DEFAULT 0
);
-- create a table for orders (one row per order):
CREATE TABLE orders (
  -- auto-numbered unique id for each order
  order_id    SERIAL PRIMARY KEY,
  -- who ordered it (a link to the customers table)
  customer_id INTEGER NOT NULL REFERENCES customers(customer_id),
  -- when it was ordered (now() = the current time)
  order_date  TIMESTAMP NOT NULL DEFAULT now(),
  -- the order's total price
  total       NUMERIC(10,2) NOT NULL DEFAULT 0
);
-- create a table for the items inside each order:
CREATE TABLE order_items (
  -- auto-numbered unique id for each line item
  order_item_id SERIAL PRIMARY KEY,
  -- which order this item belongs to (link to orders)
  order_id      INTEGER NOT NULL REFERENCES orders(order_id),
  -- which product was bought (link to products)
  product_id    INTEGER NOT NULL REFERENCES products(product_id),
  -- how many units (CHECK forces it to be more than 0)
  quantity      INTEGER NOT NULL CHECK (quantity > 0)
);

    זאת ה"מתכון השמור". קראו את ההערות (אחרי --) כדי להבין כל שלב:
    SQL · CREATE PROCEDURE
    -- define (or replace) a procedure named place_order:
CREATE OR REPLACE PROCEDURE place_order(
    -- input #1: which customer is ordering
    p_customer_id INTEGER,
    -- input #2: which product
    p_product_id  INTEGER,
    -- input #3: how many units
    p_quantity    INTEGER
)
-- written in PostgreSQL's procedural language:
LANGUAGE plpgsql
AS $$
-- declare temporary "helper" variables:
DECLARE
    -- will hold the id of the new order we create
    v_order_id INTEGER;
    -- will hold the product's price
    v_price    NUMERIC(10,2);
    -- will hold the product's current stock
    v_stock    INTEGER;
BEGIN
    -- STEP 1: read the product's price and current stock into our variables
    SELECT price, stock INTO v_price, v_stock
    FROM products WHERE product_id = p_product_id;

    -- STEP 2: safety checks before we change anything
    IF v_stock IS NULL THEN
        -- the product wasn't found -> stop with a clear error:
        RAISE EXCEPTION 'Product % does not exist', p_product_id;
    ELSIF v_stock < p_quantity THEN
        -- not enough units in stock -> stop too:
        RAISE EXCEPTION 'Not enough stock (have %, need %)', v_stock, p_quantity;
    END IF;

    -- STEP 3: create the order header row, and grab its new id
    INSERT INTO orders (customer_id, total)
    -- total = price x quantity:
    VALUES (p_customer_id, v_price * p_quantity)
    -- save the new order's id into v_order_id for the next step:
    RETURNING order_id INTO v_order_id;

    -- STEP 4: add the ordered item, linked to the order we just created
    INSERT INTO order_items (order_id, product_id, quantity)
    VALUES (v_order_id, p_product_id, p_quantity);

    -- STEP 5: subtract what was bought from the product's stock
    UPDATE products SET stock = stock - p_quantity
    WHERE product_id = p_product_id;

    -- print a friendly confirmation message:
    RAISE NOTICE 'Order % placed!', v_order_id;
END;
$$;

✍️ תרגיל קטן לבד

כתבו פונקציה בשם order_total שמקבלת order_id ומחזירה את הסכום הכולל של ההזמנה. רמז: זאת FUNCTION (כי מחזירה מספר), קוראים לה עם SELECT order_total(1);

לפתרון — לחצו כאן
SQL · פתרון
-- a function that takes an order id and returns its total price:
CREATE OR REPLACE FUNCTION order_total(p_order_id INTEGER)
-- it gives back a number:
RETURNS NUMERIC
-- written in PostgreSQL's procedural language:
LANGUAGE plpgsql
AS $$
-- a temporary variable to hold the running sum:
DECLARE v_total NUMERIC(10,2);
BEGIN
    -- add up quantity x price for every item in this order:
    SELECT SUM(oi.quantity * p.price) INTO v_total
    FROM order_items oi
    -- match each item to its product, to get the price:
    JOIN products p ON p.product_id = oi.product_id
    -- ...but only for the order we were asked about:
    WHERE oi.order_id = p_order_id;
    -- return the total (COALESCE turns NULL into 0 for an empty order):
    RETURN COALESCE(v_total, 0);
END;
$$;

-- functions are called with SELECT; show order #1's total:
SELECT order_total(1);

Triggers — "חיישני תנועה" במסד

קוד שרץ אוטומטית כשמשהו קורה בטבלה — בלי שאף אחד קרא לו. זה הקסם שמשאיר את הנתונים שלכם נקיים.

🧠 מה זה? (בשפה של בן אדם)

Trigger (בעברית: "טריגר" או "הדק") הוא קוד ששמור במסד ומופעל אוטומטית בכל פעם שקורה אירוע מסוים בטבלה — הוספת שורה (INSERT), עדכון (UPDATE) או מחיקה (DELETE).

🚪 האנלוגיה: דלת אוטומטית / חיישן תנועה

כשאתם מתקרבים לדלת אוטומטית בסופר — היא נפתחת לבד. אף אחד לא לחץ על כפתור; האירוע ("מישהו התקרב") הפעיל את התגובה ("הדלת נפתחת"). טריגר זה בדיוק זה: אתם מגדירים מראש "כשקורה X בטבלה → תעשה אוטומטית Y".

דוגמה: כשמוסיפים פריט להזמנה → המלאי יורד לבד. אף אפליקציה לא צריכה לזכור לעשות את זה — המסד עושה את זה בעצמו, תמיד.

🎬 בואו נראה את זה קורה — צעד אחר צעד

יוסי מוסיף 3 חולצות להזמנה. בלי טריגר, מישהו צריך לזכור להוריד מהמלאי. עם טריגר — זה קורה לבד, מלמעלה למטה:

⚡

↓

אירוע (הוספה) → הטריגר נדלק → תגובה (עדכון מלאי). הכל אוטומטי.

🔑 ההבדל החשוב: Procedure מול Trigger

שניהם קוד שמור במסד, אבל ההבדל הוא מי מפעיל אותם:

  • Procedure — אתם מפעילים אותה ביודעין: CALL place_order(...). כמו ללחוץ על כפתור.
  • Trigger — מפעיל את עצמו אוטומטית כשקורה אירוע. כמו חיישן תנועה. אתם לא "קוראים" לטריגר — הוא פשוט מחכה ומגיב.
יבגני: טריגרים יכולים גם להפעיל פרוצדורות, להשתרשר זה לתוך זה, ולטפל באירועים מורכבים. היום ניגע רק בבסיס המעשי שצריך כדי להבין את הרעיון. על טריגרים מתקדמים תרחיבו עם ד״ר קונדילה 👨‍🏫

🧩 מאיזה חלקים טריגר בנוי?

ב-PostgreSQL טריגר זה תמיד שני חלקים:

1. פונקציית הטריגר

פונקציה מיוחדת (RETURNS trigger) שמכילה את ה"מה לעשות". בתוכה יש שתי מילות קסם:

NEW = השורה החדשה (אחרי השינוי)
OLD = השורה הישנה (לפני השינוי)

2. הגדרת הטריגר

פקודת CREATE TRIGGER שמחברת את הפונקציה לטבלה ואומרת מתי להריץ: לפני/אחרי (BEFORE/AFTER) איזה אירוע (INSERT/UPDATE/DELETE).

💡 מה זה NEW ו-OLD? (חשוב!)

כשמעדכנים מחיר חולצה מ-49.9 ל-69.9: OLD.price = 49.9 (מה שהיה), NEW.price = 69.9 (מה שיהיה). זה מאפשר לטריגר "לראות" את השינוי ולשמור היסטוריה — בדיוק מה שנעשה עוד רגע.

בונים 2 טריגרים אמיתיים

נמשיך באותו מסד minishop מהבלוק הקודם (אותו חלון psql / Cloud SQL Studio). נבנה שני טריגרים שימושיים.

טריגר 1 · עדכון מלאי אוטומטי

במקום שמישהו יזכור להוריד מלאי — נגדיר טריגר שעושה את זה לבד בכל הוספת פריט.

  1. צרו את פונקציית הטריגר
    SQL · trigger function
    -- a special function that a trigger will run:
CREATE OR REPLACE FUNCTION trg_decrement_stock()
-- trigger functions must declare "RETURNS trigger":
RETURNS trigger
-- PostgreSQL's procedural language:
LANGUAGE plpgsql
AS $$
BEGIN
    -- NEW = the row that was just inserted (it holds product_id and quantity).
    -- update products: subtract the quantity that was just ordered,
    -- for the matching product:
    UPDATE products
    SET stock = stock - NEW.quantity
    WHERE product_id = NEW.product_id;
    -- AFTER triggers ignore the return value, so NULL is fine:
    RETURN NULL;
END;
$$;
  2. חברו את הפונקציה לטבלה
    SQL · CREATE TRIGGER
    -- give the trigger a name:
CREATE TRIGGER decrement_stock_after_insert
-- run it AFTER a row is INSERTed into order_items:
AFTER INSERT ON order_items
-- run once for every inserted row:
FOR EACH ROW
-- the function (above) to run each time:
EXECUTE FUNCTION trg_decrement_stock();
    קראו את זה כמשפט: "אחרי כל הוספה ל-order_items, לכל שורה, הרץ את הפונקציה."
  3. בדקו — הוסיפו פריט ותראו את המלאי יורד לבד
    SQL · test
    -- create an empty order first, then add a line item directly (to fire our trigger).
-- a new order for customer #2 (Rina):
INSERT INTO orders (customer_id, total) VALUES (2, 0);
-- add a line to that order. currval = the id of the order we just made; 5 Black Jeans:
INSERT INTO order_items (order_id, product_id, quantity)
VALUES (currval('orders_order_id_seq'), 2, 5);

-- check product #2's stock: it dropped from 40 to 35 automatically, thanks to the trigger:
SELECT product_id, name, stock FROM products WHERE product_id = 2;
⚠️ הערת מורה חשובה

שימו לב: גם הפרוצדורה place_order מבלוק 2 הורידה מלאי (שלב 5), וגם הטריגר הזה מוריד מלאי. במערכת אמיתית בוחרים מנגנון אחד בלבד כדי לא להוריד פעמיים.

בפועל במעבדה: אחרי שיצרתם את הטריגר — אל תקראו שוב ל-place_order, אחרת המלאי יירד פעמיים (פעם ע"י הפרוצדורה ופעם ע"י הטריגר). אם אתם רוצים להמשיך להשתמש בפרוצדורה, הסירו קודם את הטריגר: DROP TRIGGER decrement_stock_after_insert ON order_items;

טריגר 2 · יומן היסטוריית מחירים (אודיט) 🕵️

זוכרים מחלק ב׳-1 את החולצה הכחולה שהמחיר שלה עלה מ-49.9 ל-69.9, ואת מושג ה-SCD Type 2 (שמירת היסטוריה)? עכשיו נראה איך טריגר עושה את זה אוטומטית.

  1. צרו טבלת היסטוריה
    SQL
    -- a table that logs every price change:
CREATE TABLE price_history (
    -- auto-numbered id for each log entry
    history_id  SERIAL PRIMARY KEY,
    -- which product changed
    product_id  INTEGER NOT NULL,
    -- the price before the change
    old_price   NUMERIC(10,2),
    -- the price after the change
    new_price   NUMERIC(10,2),
    -- when it changed (defaults to the current time)
    changed_at  TIMESTAMP NOT NULL DEFAULT now(),
    -- which database user made the change
    changed_by  TEXT NOT NULL DEFAULT current_user
);
  2. צרו פונקציית טריגר שמשווה OLD ל-NEW
    SQL · trigger function
    -- the function our audit trigger will run:
CREATE OR REPLACE FUNCTION trg_log_price_change()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    -- OLD = the row before the change, NEW = after.
    -- IS DISTINCT FROM means "not equal" (and is safe with NULLs).
    -- only log if the price actually changed:
    IF NEW.price IS DISTINCT FROM OLD.price THEN
        -- write one log row with the product and the before/after prices:
        INSERT INTO price_history (product_id, old_price, new_price)
        VALUES (OLD.product_id, OLD.price, NEW.price);
    END IF;
    -- for row triggers, returning NEW is the conventional choice:
    RETURN NEW;
END;
$$;

-- once for every changed row:

-- run the audit function (above):

⚖️ מתי לא כדאי טריגר? — דוגמה שתבהיר

טריגר הוא "קסם נסתר": הוא רץ מאחורי הקלעים, ולא רואים אותו בקוד האפליקציה. דוגמה לבעיה אמיתית: מתכנת חדש מוסיף שורת בדיקה ל-order_items סתם כדי לנסות משהו — ופתאום המלאי במחסן יורד "לבד". הוא יבזבז שעה בחיפוש "באג" באפליקציה, בזמן שהאשם הוא טריגר שהוא בכלל לא ידע שקיים.

הכלל הפשוט: טריגרים מצוינים לחוקים קטנים, קריטיים וצפויים — אודיט, שמירת היסטוריה, שמירה על תקינות. הימנעו מלהכניס בהם לוגיקה עסקית גדולה או שרשרת טריגרים שמדליקים זה את זה — זה הופך את המערכת לבלתי ניתנת להבנה ולתחזוקה.

NoSQL עם Firebase — מסד מסוג אחר לגמרי

לא כל מסד נתונים בנוי מטבלאות ושורות. נכיר משפחה שלמה אחרת — ונבנה מסד אמיתי בדפדפן.

🧠 מה זה NoSQL? (בשפה של בן אדם)

NoSQL (מבטאים "נו-אס-קיו-אל", הכוונה: "Not Only SQL") היא משפחה של מסדי נתונים שלא משתמשים בטבלאות-עם-עמודות-קבועות, ובדרך כלל גם לא בשפת SQL. במקום מבנה נוקשה, הם נותנים גמישות ויכולת להתרחב בקלות.

🗂️ האנלוגיה: גיליון אקסל מול ערימת כרטיסיות

מסד SQL הוא כמו גיליון אקסל מסודר: יש כותרות עמודות קבועות (name, price, stock), וכל שורה חייבת להתאים בדיוק לעמודות האלה.

מסד NoSQL הוא כמו ערימת כרטיסיות: כל כרטיסייה (="מסמך") יכולה להכיל שדות שונים. לכרטיסייה של חולצה אפשר להוסיף שדה "מידות", ולכרטיסייה של ספר שדה "מחבר" — בלי לשנות שום "מבנה" מראש.

🧠 הפתרון: מה זה Load Balancer? (בשפה של בן אדם)

Load Balancer (בעברית: "מאזן עומסים") הוא "שוטר תנועה" שיושב לפני כמה שרתים זהים, ומחלק ביניהם את הבקשות הנכנסות — כך שאף שרת לא נחנק, והאתר נשאר מהיר וזמין גם אם שרת אחד נופל.

Load Balancer אמיתי ב-Cloud Shell עם NGINX

רוצים לראות את הדבר האמיתי? נבנה מאזן עומסים — לאט ובצורה ברורה. קודם נבין בדיוק מה אנחנו עומדים לעשות, בלי לקפוץ:

🧭 מה אנחנו עומדים לעשות? (הסבר לפני קוד)

מה זה "לאזן"? לפזר בקשות נכנסות בין כמה שרתים, כדי שאף שרת לא ייחנק.

מה יהיו שני ה"שרתים"? שתי תוכניות זעירות שכל אחת מגישה דף אינטרנט פשוט: אחת כותבת "Hello from SERVER 1", השנייה "SERVER 2". הן לא עושות כלום חכם — רק כדי שנראה מי ענה.

מי מאזן ביניהן? תוכנת NGINX, שנגדיר שתשב לפניהן ותחלק אליהן בקשות לפי הסדר (Round-Robin).

מהן "6 הבקשות"? נשלח 6 פעמים את אותה בקשה פשוטה לכתובת של NGINX. זה מדמה 6 משתמשים שנכנסים בזה אחר זה.

איפה רואים את האיזון? בפלט על המסך: התשובות יתחלפו — SERVER 1, SERVER 2, SERVER 1, SERVER 2... זה הסימן שהמאזן באמת חילק אותן.

עכשיו נבנה את זה בפועל, צעד-אחר-צעד:

  1. פתחו את Cloud Shell
    היכנסו ל-shell.cloud.google.com (אותו טרמינל מבלוק 2).
  2. הקימו שני שרתים זעירים
    כל אחד מגיש עמוד שאומר מי הוא:
    BASH
    # create two folders, one per "server"
mkdir -p ~/s1 ~/s2
# write server 1's web page text
echo "Hello from SERVER 1" > ~/s1/index.html
# write server 2's web page text
echo "Hello from SERVER 2" > ~/s2/index.html
# start server 1 on port 8081 ( the & means: run in the background )
( cd ~/s1 && python3 -m http.server 8081 ) &
# start server 2 on port 8082 (in the background too)
( cd ~/s2 && python3 -m http.server 8082 ) &
  3. התקינו NGINX והגדירו אותו כמאזן
    BASH
    # install the NGINX web server (it can also act as a load balancer):
sudo apt-get update && sudo apt-get install -y nginx

# write a config file that turns NGINX into a load balancer:
sudo tee /etc/nginx/conf.d/lb.conf >/dev/null <<'EOF'
# "upstream" = the pool of backend servers to balance between
upstream myapp {
    # backend #1 = our server 1
    server 127.0.0.1:8081;
    # backend #2 = our server 2
    server 127.0.0.1:8082;
}
# how NGINX itself receives visitors:
server {
    # NGINX listens on port 8080
    listen 8080;
    # forward every request to the pool (the default is round-robin)
    location / { proxy_pass http://myapp; }
}
EOF

# remove NGINX's default page so port 8080 is free for us:
sudo rm -f /etc/nginx/sites-enabled/default
# check the config is valid, then restart NGINX to apply it:
sudo nginx -t && sudo service nginx restart
  4. ראו את האיזון בפעולה
    שלחו 6 בקשות — והן יתחלפו בין השרתים (Round-Robin):
    BASH
    # send 6 requests to NGINX and print each reply
for i in $(seq 1 6); do curl -s http://localhost:8080/; done
    הפלט יתחלף: SERVER 1, SERVER 2, SERVER 1...
  5. הדגימו failover
    "הרגו" שרת אחד והריצו שוב — NGINX יזהה וישלח רק לשני:
    BASH
    # stop server 1 (the 1st background job) - this simulates a crash:
kill %1
# send 6 requests again - now only SERVER 2 answers:
for i in $(seq 1 6); do curl -s http://localhost:8080/; done
    עכשיו כל הבקשות הולכות ל-SERVER 2 בלבד. זה בדיוק מה שראיתם בהדגמה החיה למעלה.
📊 ומה הקשר שלי, האנליסט/ית, לזה?

שתי נקודות חשובות: (1) כשיש הרבה שרתים, גם הלוגים מתפזרים ביניהם — לכן אוספים אותם למקום מרכזי, וזה הופך למקור נתונים לניתוח (זוכרים את ה-log files מ-ETL בחלק ב׳-1?). (2) בדיוק כמו שמאזנים שרתי אפליקציה, מאזנים גם קריאה ממסד הנתונים בעזרת Read Replicas (עותקי-קריאה). אתם, כאנליסטים, פעמים רבות מתחברים דווקא ל-replica כדי לא להעמיס על מסד הייצור — בדיוק כמו שלמדנו בחלק ב׳-1.

🇮🇱 מה קורה בישראל?

כל אתר ישראלי גדול (בנקים, רשתות, חברות הייטק) רץ מאחורי load balancers — לרוב של ספק הענן (Google Cloud Load Balancing / AWS / Azure) או Cloudflare בקצה. ב"ימי עומס" כמו בחירות, בלאק-פריידיי או פתיחת הרשמה לאוניברסיטה, היכולת להוסיף שרתים מאחורי ה-LB היא ההבדל בין אתר שעובד לאתר שקורס.

בונים דשבורד אמיתי ב-Data Studio

נראה שתי דרכי חיבור. דרך 1 עובדת לכולם וחינמית לגמרי (גם אם השתמשתם ב-Cloud Shell). דרך 2 היא השיטה ה"מקצועית" לחיבור ישיר ל-Cloud SQL.

הדרך הכי פשוטה והכי חינמית: מוציאים את הנתונים לגיליון Google Sheets, ומחברים אותו ל-Data Studio. ככה גם מחברים נתוני Firebase (כי ל-Firestore אין connector ישיר ל-BI).

  1. הוציאו את הנתונים לגיליון

    מ-PostgreSQL: הריצו שאילתה והעתיקו את התוצאה, או ייצאו ל-CSV. שאילתה לדוגמה (כמה מכרנו מכל מוצר):

    SQL
    -- product name + total units sold:
SELECT p.name AS product, SUM(oi.quantity) AS units_sold,
       -- total revenue (quantity x price), rounded to 2 decimals:
       ROUND(SUM(oi.quantity * p.price), 2) AS revenue
-- take rows from order_items (nicknamed "oi")...
FROM order_items oi
-- ...joined to products ("p") to get each name and price:
JOIN products p ON p.product_id = oi.product_id
-- collapse into one row per product:
GROUP BY p.name
-- sort from highest revenue to lowest:
ORDER BY revenue DESC;

    מ-Firebase: ייצוא הנתונים לגיליון (ידנית למעבדה, או בעבודה אמיתית דרך התוסף הרשמי "Stream Firestore to BigQuery" או סקריפט). פתחו גיליון ב-sheets.google.com והדביקו: עמודה product, units_sold, revenue + השורות.

  2. פתחו את Data Studio
    היכנסו ל-datastudio.google.com → לחצו Create → Report (או Blank Report).
  3. חברו את הגיליון
    במסך "Add data" בחרו את ה-connector של Google Sheets → בחרו את הספרדשיט ואת הלשונית (worksheet) → Add. (Sheets לא דורש כרטיס אשראי — מושלם.)
  4. בנו גרף ראשון
    בסרגל לחצו Add a chart → בחרו Bar chart → בחלונית Setup מימין הגדירו: Dimension = product, Metric = revenue. תקבלו מיד גרף עמודות של הכנסה לפי מוצר! 🎉
  5. הוסיפו KPI ופילטר
    הוסיפו Scorecard עם המדד revenue (כרטיס "סך הכנסות"), ו-Add a control → Drop-down list על product כדי לאפשר סינון. עכשיו יש לכם דשבורד אינטראקטיבי.

אם הקמתם Cloud SQL מנוהל (דרך ב׳ בבלוק 2), אפשר לחבר את Data Studio ישירות אליו — כל שינוי במסד מתעדכן בדשבורד. זו השיטה המקצועית.

  1. פתחו כתובת IP ציבורית ל-Cloud SQL
    בקונסולה: ה-instance → Edit → Connections → Networking → סמנו Public IP. רשמו לעצמכם את כתובת ה-IP הציבורית מעמוד ה-Overview.
  2. אשרו את כתובת ה-IP של Data Studio
    באותו מסך → Authorized networks → Add a network → שם: data-studio, טווח: 142.251.74.0/23 → Save. (זה טווח כתובות היציאה של Data Studio.)
  3. חברו ב-Data Studio
    datastudio.google.com → Create → Data Source → connector PostgreSQL → לשונית BASIC:
    חיבור
    Host       = כתובת ה-IP הציבורית של ה-instance
Port       = 5432
Database   = minishop   (או postgres)
Username   = postgres
Password   = הסיסמה שקבעתם
    לחצו AUTHENTICATE → בחרו טבלה (או CUSTOM QUERY עם השאילתה מלמעלה) → CONNECT → בנו גרפים כמו בדרך 1.
  4. ⚠️ אבטחה — חובה
    אשרו רק את הטווח 142.251.74.0/23 (לעולם לא 0.0.0.0/0 שחושף לכל האינטרנט!), השתמשו בסיסמה חזקה, ובסוף — Stop/Delete ל-instance.
הערה: ה-connector של Data Studio תומך רק בטבלאות בסכימת public, מגביל ל-150,000 שורות לשאילתה, ולא תומך בחיבור Private IP / Cloud SQL Proxy — לכן צריך Public IP.
🔁 זוכרים? זה בדיוק "הלולאה של האנליסט"

מנהל שאל שאלה → אתם תרגמתם ל-SQL / חיברתם מקור → הכלי הציג גרף → הרכבתם דשבורד → המנהל קיבל החלטה. נתונים → ויזואליזציה → דשבורד → תובנה → החלטה. זה התפקיד שלכם.

סיכום: מה למדנו היום

חמישה כלים שהפכו את מסד הנתונים מ"מחסן" ל"מערכת חיה" — וחיברו הכל ל-BI.

⚙️
Stored Procedures
"מתכון שמור" במסד — קוראים בשם CALL place_order()
שומרים פעולה מורכבת פעם אחת, מרוויחים עקביות, מהירות ואבטחה. תוכנה: PostgreSQL / Cloud SQL.
⚡
Triggers
"חיישן" שרץ אוטומטית על אירוע (INSERT/UPDATE)
המלאי יורד לבד, היסטוריית מחירים נשמרת לבד. בסיס לאיכות נתונים ואודיט. תוכנה: PostgreSQL / Cloud SQL.
🔥
NoSQL · Firebase
מסמכים גמישים במקום טבלאות נוקשות
אוספים (collections) ומסמכים (documents). מצוין לזמן-אמת ואפליקציות. תוכנה: Firebase / Cloud Firestore.
⚖️
Load Balancers
"שוטר תנועה" שמחלק עומס בין שרתים
פיזור בקשות, בדיקות תקינות, failover. ככה משרתים מיליונים. תוכנה: NGINX, Google Cloud Load Balancing.
📊
הכל מתחבר ל-BI
מקורות נתונים → דשבורד שמנהל מבין
connector שולח SQL אוטומטית; גוררים שדות → גרפים. תוכנה: Data Studio (לשעבר Looker Studio).
