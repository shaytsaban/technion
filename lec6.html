Part 1 · Foundations

What is a database, really?

Forget jargon. Think of a giant, organised filing cabinet.

Imagine a giant filing cabinet

A database is just a place to store information in a very organised way. Imagine a steel filing cabinet with many drawers. Each drawer is labelled: Users, Photos, Messages. Inside each drawer are folders. Each folder is exactly one user, one photo, or one message. Every folder follows the same template — the user folder always has a name, a date of birth, a city.

A relational database is the same idea, except the cabinet is digital, infinitely fast, and the folders can refer to each other. For example, the Photo folder for “alice_001.jpg” can say “I belong to the user in folder #1138 in the Users drawer.” That little pointer — “I belong to folder #1138” — is what we call a relation. Hence: relational database.

Why not just use one giant Excel spreadsheet?

Because spreadsheets break the moment data gets real:

  • If Alice has 6 photos, you'd need 6 photo columns. What about the user with 23 photos?
  • If Alice changes her city, you'd need to update her city in every row where her name appears.
  • You can't enforce rules. Nothing stops a user from typing 1999-13-45 as their birth date in Excel.
  • If two users edit at once, one of them loses their changes.
  • It collapses past ~100,000 rows. A dating app might have 100,000,000.

A database fixes every one of those problems. It enforces structure, prevents bad data, lets thousands of users write at the same time, and stays fast at billions of rows.

What is SQL?

SQL (pronounced “sequel” or just “ess-cue-ell”) is the language we use to talk to the database. We don't click buttons — we write sentences. For example:

EXAMPLE — DON'T RUN YETSQL is just English-ish
SELECT first_name FROM profiles WHERE city = 'New York';

Read that out loud. It literally says: “Select the first name, from the table called profiles, where the city equals New York.” That's SQL. Once you see the pattern, it becomes very natural.

What is PostgreSQL?

SQL is the language; PostgreSQL (often shortened to “Postgres”) is one specific brand of database engine that understands that language. It's open-source, used by Apple, Instagram, Spotify, Reddit and the U.S. government, and it's famously reliable. Supabase — the platform we're about to use — is built on top of PostgreSQL.

Phase 1 · Engines

Turning on the database's superpowers (Extensions)

PostgreSQL ships with optional plug-ins. We need two of them.

You'll understand

  • What a PostgreSQL extension is.
  • Why we use UUIDs instead of 1, 2, 3 for user IDs.
  • What PostGIS is, and why a dating app cannot function without geospatial math.

Run this first

COPY EXACTLY THIS TEXTphase_1_extensions.sql
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
CREATE EXTENSION IF NOT EXISTS "postgis" SCHEMA "extensions";
You should see “Success. No rows returned.” Both extensions are now active.

Line-by-line walkthrough

CREATE EXTENSIONPostgres command that says “turn on a plug-in.”
IF NOT EXISTSA safety net — “only do this if it isn't already on.” Prevents an error if you run the script twice.
"uuid-ossp"The name of the first plug-in. It teaches Postgres how to generate UUIDs (Universally Unique Identifiers).
"postgis"The second plug-in. PostGIS is the industry-standard geospatial engine — it teaches Postgres how to do maps math.
SCHEMA "extensions"A tidiness instruction. It tells Postgres to install PostGIS in a dedicated folder called extensions rather than mixing it with our app tables.

Why UUIDs?

Most beginner database tutorials use auto-increment integers: 1, 2, 3, 4… Why don't we?

  • Security. If the URL of a user's profile is app.com/user/47, a hacker can just try /user/48, /user/49, and scrape every profile in your database. With UUIDs like e8a7b3c1-9d2f-4ab5-bf3e-12c8f9d0a3b6, guessing the next one is mathematically impossible.
  • No collisions. If you ever merge two databases (e.g., after a company acquisition), integer IDs collide — both databases have a user #1. UUIDs are globally unique by design.
  • Generated client-side. Your mobile app can create a UUID on the phone before the user is saved to the server — useful for offline-first apps.

Why PostGIS?

Dating apps are fundamentally location-based. “Show me single people within 10 km.” That sentence sounds simple but the math is not — the Earth is a sphere, latitude lines are not equally spaced, and a naïve calculation gives wrong answers near the poles. PostGIS solves this. It stores GPS coordinates in a special GEOGRAPHY type and gives us functions like ST_DWithin() that answer “is this point within X metres of that point?” in milliseconds, even across billions of rows.

We won't feel the magic yet — but in Phase 7, when we write a query that finds “all women aged 25–35 within 25 km of Alice,” PostGIS is what makes it possible.

Phase 2 · Foundation

Profiles & Photos — the foundation of every user

The two most important tables in any dating app.

You'll understand

  • Why we separate “a user” and “a user's photos” into two tables.
  • What a primary key, foreign key, NOT NULL, DEFAULT and CASCADE mean.
  • Which data type to pick for each kind of information.

Table 1 · The Profiles table

Every user of the app gets exactly one row in this table. It stores the “who am I” data: name, age, gender, what they're looking for, where they live, and whether they've paid for premium.

COPY EXACTLY THIS TEXTphase_2a_profiles.sql
CREATE TABLE profiles (
    id              UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    first_name      VARCHAR(50) NOT NULL,
    bio             TEXT,
    birth_date      DATE NOT NULL,
    gender          VARCHAR(20) NOT NULL,
    interested_in   VARCHAR(20) NOT NULL,
    location_point  GEOGRAPHY(Point, 4326),
    city            VARCHAR(100),
    is_premium      BOOLEAN DEFAULT FALSE,
    last_active     TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc', now()),
    created_at      TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc', now()) NOT NULL,

    CONSTRAINT valid_birth_date CHECK (birth_date < CURRENT_DATE - INTERVAL '18 years')
);

Line-by-line

CREATE TABLE profiles“Make me a new drawer in the filing cabinet, call it profiles.”
id UUID PRIMARY KEYThe unique anchor for every user. UUID is the data type; PRIMARY KEY means “this column uniquely identifies the row and can never be empty or duplicated.”
DEFAULT uuid_generate_v4()If you don't supply an ID when inserting, Postgres auto-generates one using the uuid-ossp extension we enabled.
first_name VARCHAR(50)A text field, maximum 50 characters. We use VARCHAR (variable-length string) instead of TEXT because we want to enforce a sane upper limit on names.
NOT NULLYou must provide a value. The app refuses to create a user without a first name.
bio TEXTThe bio can be long. TEXT means unlimited length. No NOT NULL — empty bios are allowed.
birth_date DATE NOT NULLStores only the date (no time). We'll calculate age from this whenever needed — it's wrong to store an age, because tomorrow it's wrong by one day.
gender VARCHAR(20)The user's gender identity. Keeping it as text (rather than 0/1) is more inclusive and easier to read.
interested_in VARCHAR(20)Who they want to see in their swipe deck: Men, Women, Everyone.
location_point GEOGRAPHY(Point, 4326)The user's GPS coordinate. Point = one (longitude, latitude) pair. 4326 = the standard ID for the GPS coordinate system used by Google Maps and every phone on Earth.
city VARCHAR(100)Human-readable city name (“Tel Aviv”). We store this separately because showing “31.0461, 34.8516” to a user is useless.
is_premium BOOLEAN DEFAULT FALSETrue/false flag for paid users. DEFAULT FALSE means new users are automatically on the free tier.
last_active TIMESTAMP…When did this user last open the app? Useful for filtering ghosts out of the swipe deck.
created_at TIMESTAMP…When the account was first made. The DEFAULT timezone('utc', now()) auto-fills it.
CONSTRAINT valid_birth_date CHECK…A custom rule: birth date must be at least 18 years before today. Postgres will refuse to insert anyone under 18. Legal compliance, enforced at the database level.

Pro insight: defence in depth

You might say: “The mobile app already validates that the user is 18+, why duplicate the check in the database?” Because the mobile app can be bypassed. A determined attacker can call your API directly without using your app. The database is the last line of defence. Putting rules here means they're enforced no matter what code calls them.

Table 2 · The Profile Media (Photos) table

A user has many photos. We can't put 6 photo columns in the profiles table (what about user #847 with 23 photos?). So we make a separate table where each row is one photo, and the photo points back to its owner.

COPY EXACTLY THIS TEXTphase_2b_profile_media.sql
CREATE TABLE profile_media (
    media_id     UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    user_id      UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
    storage_url  TEXT NOT NULL,
    is_primary   BOOLEAN DEFAULT FALSE,
    display_order INTEGER DEFAULT 0,
    created_at   TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc', now()) NOT NULL
);
media_id UUID PRIMARY KEYEvery photo gets its own unique ID, so we can later delete “photo #3” without affecting the others.
user_id UUID NOT NULLThe owner of the photo. Must be present.
REFERENCES profiles(id)This is the foreign key — the most important concept in relational databases. It physically chains this row to the profiles table. Postgres will refuse to insert a photo for a non-existent user.
ON DELETE CASCADEThe clean-up rule. If a user deletes their account, Postgres automatically removes all their photos in this table — no orphaned files, no manual cleanup.
storage_url TEXT NOT NULLThe URL of the actual image file (stored in Supabase Storage). The image itself isn't in the database — only the link to it.
is_primary BOOLEANMarks the user's main profile picture (the one shown on the swipe card).
display_order INTEGERLets the user reorder their photos. Photo with order 0 shows first, order 1 second, etc.

This is what “relational” means

We now have two tables that relate to each other. The line user_id UUID REFERENCES profiles(id) is the relation. If you imagine the database as a spider's web, this is the first thread connecting two nodes. Every other table we build today will weave more threads. That web is your dating app.

Phase 3 · Interactions

Swipes & Matches — the engine of any dating app

A swipe is “Alice liked Bob.” A match is “Alice liked Bob, AND Bob liked Alice.”

Table 3 · User Swipes

Every left swipe and every right swipe is recorded here. We need a permanent record because (a) we never want to show the same person twice, and (b) we need to detect mutual likes to create matches.

COPY EXACTLY THIS TEXTphase_3a_swipes.sql
CREATE TABLE user_swipes (
    swipe_id        UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    swiper_id       UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
    swiped_user_id  UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
    is_liked        BOOLEAN NOT NULL,
    created_at      TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc', now()) NOT NULL,

    CONSTRAINT unique_swipe UNIQUE (swiper_id, swiped_user_id),
    CONSTRAINT no_self_swipe CHECK (swiper_id <> swiped_user_id)
);
swiper_idThe person doing the swiping.
swiped_user_idThe person being swiped on.
REFERENCES profiles(id)Both columns point to the same parent table. This is called a self-referencing relationship through an intermediary — perfectly normal in social apps.
is_liked BOOLEAN NOT NULLTRUE = right swipe (like). FALSE = left swipe (pass).
UNIQUE (swiper_id, swiped_user_id)A composite uniqueness rule: Alice can swipe on Bob exactly once in history. If she tries again, the database refuses. This is why Tinder never re-shows you the same person.
CHECK (swiper_id <> swiped_user_id)You can't swipe on yourself. Sounds obvious, but bugs happen — enforce it at the database.

Table 4 · Matches

When two users have liked each other, we create a match. A match unlocks the ability to chat.

COPY EXACTLY THIS TEXTphase_3b_matches.sql
CREATE TABLE matches (
    match_id    UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    user_id_1   UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
    user_id_2   UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
    is_active   BOOLEAN DEFAULT TRUE,
    created_at  TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc', now()) NOT NULL,

    CONSTRAINT unique_match UNIQUE (user_id_1, user_id_2),
    CONSTRAINT no_self_match CHECK (user_id_1 <> user_id_2),
    CONSTRAINT ordered_pair  CHECK (user_id_1 < user_id_2)
);
user_id_1, user_id_2The two matched people. Names are intentionally neutral — neither one is “the matcher” or “the matched.”
is_active BOOLEAN DEFAULT TRUEIf someone “unmatches,” we set this to FALSE rather than delete the row — we keep the audit trail and can hide it from the UI.
UNIQUE (user_id_1, user_id_2)Prevents duplicate matches.
CHECK (user_id_1 < user_id_2)A subtle but clever rule: we force the smaller UUID to always go first. This stops us from accidentally creating two matches for the same pair (one as (Alice, Bob) and one as (Bob, Alice)). It guarantees one canonical row per pair.

How does a match actually get created?

In a real app, when a user swipes right, your server runs: “Did the other person already swipe right on me?” If yes, insert into the matches table. We'll do exactly this manually in Phase 6, and later you could automate it with a database trigger.

Phase 4 · Communication

Messages & Safety

Conversations live inside matches. Safety is non-negotiable.

Table 5 · Messages

Every chat message is one row. Messages belong to a match (which is the conversation), and we record who sent each one.

COPY EXACTLY THIS TEXTphase_4a_messages.sql
CREATE TABLE messages (
    message_id  UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    match_id    UUID NOT NULL REFERENCES matches(match_id) ON DELETE CASCADE,
    sender_id   UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
    content     TEXT NOT NULL,
    is_read     BOOLEAN DEFAULT FALSE,
    created_at  TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc', now()) NOT NULL,

    CONSTRAINT non_empty_content CHECK (length(trim(content)) > 0)
);
match_id REFERENCES matchesThe conversation. Every message belongs to exactly one match.
sender_id REFERENCES profilesWho typed the message. The other participant in the match is implicitly the recipient.
content TEXT NOT NULLThe actual message body. No length limit (well, 1 GB, but realistically no one types that).
is_read BOOLEAN DEFAULT FALSEFor the “Read” receipt feature. New messages are unread by default.
non_empty_content CHECKRefuses to save blank or whitespace-only messages — a common UX bug.

Table 6 · Blocks & Reports

If user A blocks user B, A never sees B again — in the swipe deck, in search, anywhere. Reports go to moderators.

COPY EXACTLY THIS TEXTphase_4b_blocks_reports.sql
CREATE TABLE blocks_reports (
    block_id        UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    reporter_id     UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
    blocked_user_id UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
    reason          TEXT,
    severity        VARCHAR(20) DEFAULT 'block',
    created_at      TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc', now()) NOT NULL,

    CONSTRAINT unique_block UNIQUE (reporter_id, blocked_user_id),
    CONSTRAINT no_self_block CHECK (reporter_id <> blocked_user_id),
    CONSTRAINT valid_severity CHECK (severity IN ('block', 'report', 'block_and_report'))
);
reporter_idThe person who clicked “block” or “report.”
blocked_user_idThe target.
reason TEXTOptional free-text reason (e.g. “inappropriate photos,” “fake profile,” “rude messages”).
severityWas this just a soft block (don't show this person to me) or a formal report (please review them, moderation team)?
CHECK severity IN…Allow-list of values. Anything else throws an error.
Phase 5 · Speed

Indexes — making everything fast

Without indexes, finding “users near me” takes 30 seconds. With indexes, 4 milliseconds.

An index is a behind-the-scenes shortcut. Imagine looking for “Smith” in a 1000-page phone book. Without an index, you read every page. With an index (the alphabetical tabs on the side), you jump straight to S. Same idea here.

For every column we frequently search by, we add an index. For our dating app, the critical ones are: location, foreign keys (used in JOINs), and timestamps.

COPY EXACTLY THIS TEXTphase_5_indexes.sql
-- Find users by location (PostGIS spatial index)
CREATE INDEX idx_profiles_location ON profiles USING GIST (location_point);

-- Find a user's photos quickly
CREATE INDEX idx_media_user_id ON profile_media (user_id);

-- Find all swipes by a given user
CREATE INDEX idx_swipes_swiper ON user_swipes (swiper_id);
CREATE INDEX idx_swipes_swiped ON user_swipes (swiped_user_id);

-- Find a user's matches
CREATE INDEX idx_matches_user1 ON matches (user_id_1);
CREATE INDEX idx_matches_user2 ON matches (user_id_2);

-- Load a chat conversation in order
CREATE INDEX idx_messages_match_time ON messages (match_id, created_at DESC);

-- Find blocks involving a user
CREATE INDEX idx_blocks_reporter ON blocks_reports (reporter_id);
CREATE INDEX idx_blocks_blocked ON blocks_reports (blocked_user_id);

Why USING GIST for location?

Standard indexes are great for numbers and text, but useless for “within 10 km of a point.” A GIST index (Generalized Search Tree) is built for spatial and range queries — it's how PostGIS finds nearby points in milliseconds.

Why do messages need a composite index (match_id, created_at DESC)?

When you open a chat, your app runs: “get all messages for this match, newest first.” A composite index on both columns simultaneously answers that query without a single millisecond of scanning. It's the difference between a snappy chat and a janky one.

Alternative approach (for advanced students)

Instead of hardcoding UUIDs, real production scripts use Postgres' RETURNING clause or DO-blocks with variables. For example:

DO $$
DECLARE alice_id UUID; bob_id UUID;
BEGIN
  INSERT INTO profiles (first_name, birth_date, gender, interested_in)
    VALUES ('Alice', '1995-05-12', 'Women', 'Men') RETURNING id INTO alice_id;
  INSERT INTO profiles (first_name, birth_date, gender, interested_in)
    VALUES ('Bob',   '1992-11-23', 'Men',   'Women') RETURNING id INTO bob_id;
  INSERT INTO user_swipes (swiper_id, swiped_user_id, is_liked)
    VALUES (alice_id, bob_id, true);
END $$;

Cleaner, but harder for beginners to trace. Stick with hardcoded UUIDs while learning.

Phase 7 · Asking questions

Powerful queries — making the database talk

Twelve queries that mirror exactly what a real dating app asks its database every second.

Each query below has a goal (“what does the app need?”), the SQL, and an explanation of every clause. Run them one at a time in the SQL Editor and read the results.

Query 1 · Show all users

Goal: admin dashboard — list everyone with their age.

COPY EXACTLY THIS TEXTquery_01_all_users.sql
SELECT
    first_name,
    city,
    gender,
    interested_in,
    EXTRACT(YEAR FROM age(birth_date)) AS age,
    is_premium
FROM profiles
ORDER BY first_name;

EXTRACT(YEAR FROM age(birth_date)) calculates the user's current age from their birth date. age() returns an interval like “30 years 4 months”; EXTRACT(YEAR FROM …) pulls just the years. Never store age — always calculate it.

Query 2 · A single user's full profile (with photos)

Goal: the “view profile” screen — needs the user plus all their photos in order.

COPY EXACTLY THIS TEXTquery_02_user_with_photos.sql
SELECT
    p.first_name,
    p.bio,
    p.city,
    EXTRACT(YEAR FROM age(p.birth_date)) AS age,
    m.storage_url,
    m.is_primary,
    m.display_order
FROM profiles p
LEFT JOIN profile_media m ON m.user_id = p.id
WHERE p.first_name = 'Alice'
ORDER BY m.display_order;

Understanding JOIN

A JOIN glues two tables together using a relationship. Here we say: “take each profile row, and for every photo whose user_id matches the profile's id, glue them side-by-side.” LEFT JOIN means “keep the user even if they have zero photos.” p and m are just nicknames (aliases) to type less.

Query 3 · Users near me (geospatial magic)

Goal: the swipe deck — find people within 50 km of Alice.

COPY EXACTLY THIS TEXTquery_03_users_nearby.sql
SELECT
    other.first_name,
    other.city,
    ROUND( ST_Distance(alice.location_point, other.location_point)::numeric / 1000, 1 ) AS km_away
FROM profiles alice
JOIN profiles other
  ON ST_DWithin(alice.location_point, other.location_point, 50000)  -- 50 km in metres
WHERE alice.first_name = 'Alice'
  AND other.id <> alice.id
ORDER BY km_away;

The PostGIS payoff

ST_DWithin(a, b, 50000) means “is point a within 50,000 metres of point b?” ST_Distance returns the actual distance in metres; we divide by 1000 to get km and round to one decimal. With our GIST index on location_point, this query is instant even at millions of rows.

Query 4 · The swipe deck (filtered)

Goal: show Alice candidates she hasn't swiped on yet, who match her preferences, and who haven't been blocked.

COPY EXACTLY THIS TEXTquery_04_swipe_deck.sql
WITH me AS (
    SELECT * FROM profiles WHERE first_name = 'Alice'
)
SELECT
    p.first_name,
    p.bio,
    p.city,
    EXTRACT(YEAR FROM age(p.birth_date)) AS age
FROM profiles p, me
WHERE p.id <> me.id
  AND p.gender = me.interested_in            -- gender preference
  AND p.interested_in IN (me.gender, 'Everyone')  -- mutual interest
  AND p.id NOT IN (                          -- exclude already-swiped
        SELECT swiped_user_id FROM user_swipes WHERE swiper_id = me.id
  )
  AND p.id NOT IN (                          -- exclude users I blocked
        SELECT blocked_user_id FROM blocks_reports WHERE reporter_id = me.id
  )
  AND p.id NOT IN (                          -- exclude users who blocked me
        SELECT reporter_id FROM blocks_reports WHERE blocked_user_id = me.id
  )
ORDER BY p.last_active DESC;

This is the heart of any dating app

The WITH me AS (...) is called a Common Table Expression (CTE) — a temporary, named result we can refer to. Then we chain filters: not me, matches preferences, not yet swiped, no blocks either way. This is the exact logic Tinder runs millions of times per minute.

Query 5 · All of Alice's matches

COPY EXACTLY THIS TEXTquery_05_my_matches.sql
SELECT
    m.match_id,
    CASE
        WHEN m.user_id_1 = alice.id THEN other1.first_name
        ELSE other2.first_name
    END AS matched_with,
    m.created_at
FROM matches m
JOIN profiles alice ON alice.first_name = 'Alice'
LEFT JOIN profiles other1 ON other1.id = m.user_id_2
LEFT JOIN profiles other2 ON other2.id = m.user_id_1
WHERE alice.id IN (m.user_id_1, m.user_id_2)
  AND m.is_active = true
ORDER BY m.created_at DESC;

CASE WHEN…THEN…ELSE…END is SQL's if-statement. Because Alice might be in either column of the match (user_id_1 or user_id_2), we need to pick whichever isn't her.

Query 6 · Recent conversations with last message preview

Goal: the inbox screen. For every match, show the most recent message and how long ago.

COPY EXACTLY THIS TEXTquery_06_inbox.sql
SELECT DISTINCT ON (m.match_id)
    m.match_id,
    msg.content        AS last_message,
    msg.created_at     AS sent_at,
    msg.is_read,
    sender.first_name  AS sent_by
FROM matches m
JOIN messages msg  ON msg.match_id = m.match_id
JOIN profiles sender ON sender.id = msg.sender_id
ORDER BY m.match_id, msg.created_at DESC;

DISTINCT ON (m.match_id) is a Postgres trick: it keeps only the first row for each match (after the ORDER BY). Combined with ORDER BY m.match_id, msg.created_at DESC, “first” means “most recent message.”

Query 7 · Unread messages count per match

COPY EXACTLY THIS TEXTquery_07_unread_counts.sql
SELECT
    m.match_id,
    COUNT(*) FILTER (WHERE msg.is_read = false) AS unread,
    COUNT(*) AS total
FROM matches m
JOIN messages msg ON msg.match_id = m.match_id
GROUP BY m.match_id
ORDER BY unread DESC;

COUNT(*) FILTER (WHERE ...) counts rows that match a condition — a powerful Postgres feature. GROUP BY tells Postgres to bucket rows by match_id before counting.

Query 8 · Most popular users (who got the most likes)

COPY EXACTLY THIS TEXTquery_08_most_popular.sql
SELECT
    p.first_name,
    p.city,
    COUNT(s.swipe_id) AS likes_received
FROM profiles p
LEFT JOIN user_swipes s
  ON s.swiped_user_id = p.id AND s.is_liked = true
GROUP BY p.id, p.first_name, p.city
ORDER BY likes_received DESC;

Query 9 · Pending likes (someone liked me but I haven't swiped back)

Goal: the “Likes You” screen — premium feature on most apps.

COPY EXACTLY THIS TEXTquery_09_likes_you.sql
SELECT
    liker.first_name AS liked_you,
    liker.city
FROM user_swipes s
JOIN profiles me     ON me.first_name = 'Alice'
JOIN profiles liker  ON liker.id = s.swiper_id
WHERE s.swiped_user_id = me.id
  AND s.is_liked = true
  AND liker.id NOT IN (
       SELECT swiped_user_id FROM user_swipes WHERE swiper_id = me.id
  );

Query 10 · Are Alice and Bob matched?

COPY EXACTLY THIS TEXTquery_10_pair_status.sql
SELECT EXISTS (
    SELECT 1 FROM matches m
    JOIN profiles a ON a.first_name = 'Alice'
    JOIN profiles b ON b.first_name = 'Bob'
    WHERE m.is_active = true
      AND (
          (m.user_id_1 = a.id AND m.user_id_2 = b.id) OR
          (m.user_id_1 = b.id AND m.user_id_2 = a.id)
      )
) AS are_matched;

EXISTS returns just true or false — perfect for yes/no questions. Faster than counting.

Query 11 · The activity feed (everything that happened in the last 24 hours)

COPY EXACTLY THIS TEXTquery_11_activity_feed.sql
SELECT 'message' AS kind, sender.first_name AS who, msg.content AS detail, msg.created_at AS happened_at
FROM messages msg
JOIN profiles sender ON sender.id = msg.sender_id
WHERE msg.created_at > now() - interval '24 hours'

UNION ALL

SELECT 'match', p1.first_name || ' & ' || p2.first_name, 'matched', m.created_at
FROM matches m
JOIN profiles p1 ON p1.id = m.user_id_1
JOIN profiles p2 ON p2.id = m.user_id_2
WHERE m.created_at > now() - interval '24 hours'

ORDER BY happened_at DESC;

UNION ALL stacks two queries vertically — like concatenating spreadsheets. Both must return the same number of columns, in the same order.

Query 12 · Database health check

COPY EXACTLY THIS TEXTquery_12_health.sql
SELECT
    (SELECT COUNT(*) FROM profiles)        AS total_users,
    (SELECT COUNT(*) FROM profiles WHERE is_premium) AS premium_users,
    (SELECT COUNT(*) FROM profile_media)   AS total_photos,
    (SELECT COUNT(*) FROM user_swipes)     AS total_swipes,
    (SELECT COUNT(*) FROM user_swipes WHERE is_liked) AS total_likes,
    (SELECT COUNT(*) FROM matches WHERE is_active)    AS active_matches,
    (SELECT COUNT(*) FROM messages)        AS total_messages,
    (SELECT COUNT(*) FROM blocks_reports)  AS total_blocks;
If this last query returns the numbers you expect (8 users, 5 premium-or-non, 15 photos, 16 swipes, 6 matches, 9 messages, 1 block), your database is perfectly wired. You just built a working dating app back-end.
Phase 8 · The map

The ERD — your database's map

An Entity-Relationship Diagram shows your tables as boxes and your relationships as arrows.

Open Supabase's Schema Visualizer

  1. In the left dark menu, click Database.
  2. In the secondary menu that appears, click Schema Visualizer.
  3. Supabase auto-draws every one of your tables as a card, with lines connecting them via foreign keys.
  4. Drag the cards around. Zoom in. Notice the arrows.

What you're actually looking at

Here is a stylised version of what the ERD shows. Boxes are tables. Arrows are foreign keys. Notice how profiles sits at the centre — almost every other table points at it.

Reading the diagram like a pro

  • The hub. profiles sits in the centre. Five of the six tables point at it. This tells us the user is the central concept of the app — everything else describes what users do.
  • Double arrows. Some tables connect to profiles with two arrows (user_swipes, matches, blocks_reports). That's because each row in those tables involves two users. The two arrows are the swiper & swiped, the two matched users, the reporter & blocked.
  • The chain through messages. Messages point at both matches and profiles. That means a message belongs to a conversation AND has a sender — both relationships are required.
  • 1:N notation. “1:N” means “one to many.” One profile has many photos. One match has many messages. The arrow points from the “many” side to the “one” side.

Why the ERD is invaluable

  • Detecting design mistakes. If you ever see a table with no arrows going in or out, it's probably isolated and unused. If you see a table connected to everything, you probably have a god-table that should be split.
  • Onboarding teammates. A new developer can understand your entire schema in 60 seconds by looking at the ERD. Compare that to reading 500 lines of CREATE TABLE statements.
  • Planning new features. Want to add “date suggestions inside chat”? Look at the ERD: should it be a new table linked to messages? To matches? Should it have a foreign key to a venues table? The ERD is your whiteboard.
  • Spotting missing relationships. If you forgot a foreign key, the ERD shows it as a floating box with no connections — instantly visible.

One ERD habit to develop

Before you write a single line of SQL for a new feature, draw the ERD by hand on paper. Boxes for tables, arrows for relationships. If you can't draw it, you don't understand it yet. The SQL is just the translation of the drawing.

Phase 9 · Beyond this guide

You did it. Now what?

A real dating app needs a few more layers on top of this foundation.

Congratulations — you've built a production-grade relational schema for a dating app. To turn this into a launched product, the next steps are:

Row-Level Security (RLS)

Right now, anyone with database access can read every message. RLS adds rules like “a user can only read messages where they are the sender or recipient.” Supabase has a one-click RLS editor — turn it on for every table before launch.

Supabase Auth

Connect the profiles.id column to Supabase's built-in auth.users table. Now sign-up, log-in, password reset and OAuth (Google, Apple) all work without writing them.

Supabase Storage

Create a public bucket named profile-photos. Upload from your mobile app. The URLs you store in profile_media.storage_url will point there.

Database triggers

Write a trigger so the matches table is automatically populated whenever two users mutually like each other. The app no longer has to check — Postgres does.

Real-time chat

Enable Realtime on the messages table. Your mobile app subscribes, and every new message pushes instantly — no polling, no refresh.

Mobile UI

Build the swipe deck in React Native, Flutter, or SwiftUI. Talk to your Supabase database through the auto-generated API. The schema you built today is ready to power millions of users.

You started this guide knowing nothing about databases. You finished it having designed, built, populated, indexed and queried a real dating-app back-end. That's a serious engineering skill.
